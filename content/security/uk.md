# Модель безпеки

Безпека NimbusNexus тримається на чотирьох опорах: API-ключі — єдиний спосіб автентифікації, проєкти — одиниця ізоляції, області дії звужують те, що може робити кожен ключ, а журнали аудиту записують усе, що мало значення. Ця сторінка — концептуальний огляд; подробиці про кожну частину — на окремих сторінках довідника.

## Межа довіри {#trust-boundary}

Межа довіри — це окремий проєкт. Усередині проєкту кожен авторизований клієнт може впливати на кожен ресурс. Між проєктами ніщо ні на що не впливає — проєкти не мають спільних мереж, спільних дозволів IAM чи спільних квот.

Так задумано. Якщо два навантаження треба ізолювати одне від одного (продакшн від staging, клієнта A від клієнта B), розмістіть їх у різних проєктах. Не намагайтеся ізолювати їх через області дії чи мітки всередині одного проєкту — області дії обмежують, що може робити окремий ключ, але скомпрометований адміністраторський ключ у проєкті все одно має повний доступ.

## API-ключі {#api-keys}

Єдині облікові дані, які приймає API, — це API-ключ. Немає ні OAuth-процесу для кожного користувача, ні процесу підпису JWT, ні mTLS — лише bearer-ключі. Чому механізм один: кожен додатковий тип облікових даних збільшує поверхню атаки (процес випуску, процес відкликання, поширення), і ми воліємо зробити непроникним той, що маємо.

Ключі:

- **Привʼязані до проєкту.** Ключ, привʼязаний до проєкту `acme-prod`, не може нічого прочитати в `acme-staging`, навіть у тому самому акаунті.
- **Довгострокові, але з ротацією.** Ключ, створений сьогодні, діє, доки ви його не ротуєте чи не відкличете. Ротація має 24-годинне вікно перекриття, тож новий ключ можна розгорнути без простою.
- **Створюються лише в дашборді.** API для створення ключів немає. Скомпрометований ключ не може створити інший ключ — відновлення має йти через окремий канал.

Формат запиту, список областей дії, процес ротації й коди помилок описано на сторінці [Автентифікація](/docs/authentication).

## Області дії {#scopes}

Кожен ключ має набір областей дії, які обмежують, що він може робити у своєму проєкті. Повний список відповідає типам ресурсів:

- `vms:read`, `vms:write`, `vms:create`, `vms:delete`
- `databases:*`, `block-storage:*`, `object-storage:*`, `iam:*`, ...

Області дії — адитивна система: ключ має обʼєднання всіх областей дії, які йому надано. Немає ні заперечень, ні правил пріоритету, ні ролей, у яких треба розбиратися.

Правильний патерн: **починайте вузько, розширюйте після збою**. Створіть ключ лише з тими областями дії, які, як ви знаєте, вам потрібні; якщо якоїсь бракує, хай застосунок отримає `403 forbidden` (`details.reason` дорівнює `scope`), і тоді додайте її. Так помилки на кшталт «я випадково дав CI-завданню права адміністратора» виявляються під час розробки, а не в продакшні.

## Проєкти {#projects}

Проєкти — найсильніший примітив ізоляції: це межа ресурсів, межа білінгу й межа керування доступом. Користувач із правами адміністратора в проєкті `acme-prod` не бачить ресурсів проєкту `acme-staging`, якщо не має там також прав адміністратора (чи будь-якої області дії).

Більшості команд потрібен **щонайменше один проєкт на кожне середовище** (`prod`, `staging`, `dev`). Причина: скомпрометований dev-ключ не повинен діставати до продакшн-даних. Ще краще — один проєкт на кожну комбінацію середовища й сервісу (`acme-prod-api`, `acme-prod-batch`), щоб через витік облікових даних у пакетному завданні не можна було прочитати дані клієнтів API.

Формат ресурсу й механіку ієрархії описано на сторінці [Проєкти](/docs/api/projects).

## Мережева модель {#network}

За замовчуванням VM ізольована. Щоб вона мала вихідний доступ до інтернету, підʼєднайте [плаваючий IP](/docs/api/floating-ips) або розмістіть її в мережі з маршрутизатором. Щоб вона приймала вхідний трафік, підʼєднайте плаваючий IP і (як правило) поставте перед нею [групу безпеки](/docs/api/security-groups) як фаєрвол з відстеженням стану.

Міжпроєктної мережевої взаємодії не існує. VM у проєкті `acme-prod` не може надсилати трафік до VM у проєкті `acme-staging`, і крапка, навіть через приватні IP — віртуальний комутатор, на якому все працює, забезпечує ізоляцію на рівні проєктів. Якщо вам потрібна міжпроєктна взаємодія (рідко), правильний патерн — «виставити публічний API і викликати його через інтернет»: межа довіри та сама, ніби два навантаження належали різним компаніям.

VPC peering і подібні міжпроєктні мережеві примітиви можуть зʼявитися пізніше; зараз їх немає, і це навмисне обмеження.

## Журнали аудиту {#audit}

Кожен автентифікований запит, що змінює стан, записується в журнал із такими полями:

- `request_id` — той самий ідентифікатор, що зʼявляється у відповідях із помилками
- `key_id` — який ключ зробив виклик (префікс + останні 4 символи, ніколи не повний секрет)
- `user_id` — користувач, який створив ключ
- `operation` — `vms.create`, `database.delete` тощо
- `resource_id` — ресурс, якого це стосувалося
- `project_id` — проєкт
- `result` — `success`, `validation_error`, `unauthorized` тощо
- `client_ip` — IP джерела
- `timestamp` — ISO 8601 UTC

Журнали аудиту доступні в дашборді (з фільтрами й експортом) і через API аудиту IAM. Строк зберігання — **365 днів** для рівнів Free і Starter, **2 роки** для Production і налаштовується для Enterprise.

`GET`-запити записуються для ресурсів, позначених як чутливі (IAM, білінг, способи оплати); звичайні читання (список VM) не записуються, щоб обсяг журналів лишався керованим. Список «чутливих читань» наведено на сторінці довідника IAM.

## Дані в стані спокою {#at-rest}

- **Блокові томи:** AES-256-XTS з окремим ключем для кожного тому, ключами керуємо ми. Ключі шифрування, якими керує клієнт (CMK), є в планах розвитку; поки що недоступні.
- **Обʼєктне сховище:** за замовчуванням AES-256 на боці сервера; доступні SSE-C (ключі, які надає клієнт) і SSE-KMS (CMK через KMS).
- **Бекапи + снапшоти:** те саме шифрування, що й у вихідного тому/обʼєкта.
- **Бекапи баз даних:** те саме шифрування + власне шифрування даних у стані спокою рушієм бази даних, якщо його ввімкнено.

## Дані під час передавання {#in-transit}

Увесь трафік API йде через TLS 1.3 (TLS 1.2 приймається; старіші версії шлюз відхиляє). Підключення до обʼєктного сховища й баз даних використовують TLS 1.3, а наші сертифікати ротуються автоматично. Доставки вебхуків від нас до вас використовують TLS; простих URL `http://` для ендпоінтів вебхуків ми не приймаємо.
