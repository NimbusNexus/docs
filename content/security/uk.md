# Модель безпеки

В API інфраструктури те, що можуть робити облікові дані, обмежують три речі: проєкти — одиниця ізоляції, ролі визначають, що ключ може робити у своєму проєкті, а правила доступу звужують коло викликів, які він може робити. Ця сторінка — концептуальний огляд; подробиці про кожну частину — на окремих сторінках довідника.

## Межа довіри {#trust-boundary}

Межа довіри — це окремий проєкт. Усередині проєкту кожен авторизований клієнт може впливати на кожен ресурс. Між проєктами ніщо ні на що не впливає, якщо ви самі не відкриєте доступ: ресурс належить одному проєкту, квоти діють окремо для кожного проєкту, а ключ працює в одному проєкті.

Так задумано. Якщо два навантаження треба ізолювати одне від одного (продакшн від staging, клієнта A від клієнта B), розмістіть їх у різних проєктах. Не намагайтеся ізолювати їх через правила доступу всередині одного проєкту: вони обмежують, що може робити окремий ключ, але інший ключ у проєкті з ширшими правилами все одно має повний доступ.

## Облікові дані {#api-keys}

API приймає два види облікових даних: **API-ключ** у заголовку `X-API-Key` — для інструментів і скриптів, і **сесію, у яку ви ввійшли**, — для людини в дашборді.

Ключі:

- **Привʼязані до проєкту.** Ключ, привʼязаний до проєкту `acme-prod`, не може нічого прочитати в `acme-staging`, навіть у тому самому акаунті.
- **Особисті.** Кожен ключ належить людині, яка його створила, і діє з ролями, які вона має.
- **Створюються із сесії, у яку ви ввійшли**, — у дашборді або через `POST /api/v1/api_keys/`.
- **Діють, доки ви їх не видалите** або доки не настане заданий вами `expires_at`. Окремого виклику для ротації немає: щоб замінити ключ, створіть новий, переведіть на нього свої інструменти, а потім видаліть старий.

Формат запиту й подробиці описано на сторінці [Автентифікація](/docs/authentication).

## Ролі й правила доступу {#scopes}

Ключ діє з `roles` у своєму проєкті, а його `access_rules` обмежують, які виклики він може робити: кожне правило вказує сервіс, метод і шлях. `unrestricted: true` означає відсутність правил доступу, тож ключ може робити будь-який виклик, який дозволяють його ролі. Ключ без жодного з них може лише прочитати власну сесію.

Правильний патерн: **починайте вузько, розширюйте після збою**. Створіть ключ лише з тими викликами, які, як ви знаєте, вам потрібні. На виклик поза ними API відповідає `403`, і ви створюєте новий ключ, який його охоплює. Так помилки на кшталт «я випадково дав CI-завданню права адміністратора» виявляються під час розробки, а не в продакшні.

## Проєкти {#projects}

Проєкти — найсильніший примітив ізоляції: це межа ресурсів і межа керування доступом. Білінг ведеться на рівні робочого простору. Людина з роллю в проєкті `acme-prod` не бачить ресурсів проєкту `acme-staging`, якщо не має ролі й там.

Більшості команд потрібен **щонайменше один проєкт на кожне середовище** (`prod`, `staging`, `dev`). Причина: скомпрометований dev-ключ не повинен діставати до продакшн-даних. Ще краще — один проєкт на кожну комбінацію середовища й сервісу (`acme-prod-api`, `acme-prod-batch`), щоб через витік облікових даних у пакетному завданні не можна було прочитати дані клієнтів API.

Подробиці описано на сторінці [Проєкти](/docs/api/projects).

## Мережева модель {#network}

До VM у приватній мережі не можна дістатися з інтернету. Щоб мати вихідний доступ до інтернету, підʼєднайте мережу до [маршрутизатора](/docs/api/routers) із зовнішнім шлюзом. Щоб приймати вхідний трафік, підʼєднайте [плаваючий IP](/docs/api/floating-ips). Кожна VM має щонайменше одну [групу безпеки](/docs/api/security-groups), яка забороняє весь вхідний трафік, доки ви його не дозволите.

Кожна мережа належить одному проєкту. VM у проєкті `acme-prod` не може надсилати трафік до VM у проєкті `acme-staging` через приватні IP, якщо ви не надасте їм спільну мережу ([Спільні мережі](/docs/api/network-sharing)). Пірингу між мережами проєктів немає. В інших випадках патерн такий: «виставити публічний API і викликати його через інтернет» — межа довіри та сама, ніби два навантаження належали різним компаніям.

## Дані під час передавання {#in-transit}

API працює через HTTPS. У продукті [Webhooks](/docs/product-webhooks) доставки теж використовують TLS: URL ендпоінта має бути `https`.

## Повідомлення про вразливість {#disclosure}

Знайшли проблему з безпекою? Не відкривайте issue на GitHub (він публічний) і не надсилайте звичайне звернення в підтримку (його довше сортуватимуть). [Форма повідомлення про вразливість]({{BASE_URL}}/contact/security) потрапляє безпосередньо до команди безпеки, приймає тексти, зашифровані PGP, а отримання підтверджується протягом 24 годин.

Умови «безпечної гавані» наведено на [{{BASE_URL}}/legal/security-policy]({{BASE_URL}}/legal/security-policy). Сумлінні дослідження ми вітаємо.
