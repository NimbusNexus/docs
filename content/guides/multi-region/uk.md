# Failover між регіонами

Плаваючі IP існують у межах регіону — переміщатися між регіонами вони не можуть. Для міжрегіонального failover (відмова цілого регіону, погіршення затримки в регіоні) правильний примітив — маршрутизація на рівні DNS із перевірками стану. Маршрутизація за затримкою спрямовує кожного користувача в найближчий справний регіон; у разі збою регіону рівень DNS виводить цей регіон із ротації.

Цільовий RTO для такої конфігурації: **20–60 секунд** залежно від TTL і того, як швидко ваші DNS-резолвери повторюють запит.

## Що ви налаштуєте {#overview}

```text
                    your customers
                          │
                  app.example.com  ← DNS A record set
                          │
            ┌─────────────┴─────────────┐
            ↓                           ↓
       us-east-1                   eu-central-1
   (203.0.113.5/32)             (198.51.100.5/32)
        VM-A                        VM-B
        │                            │
        └─ replicated DB ───────────┘
              (logical replication)
```

DNS повертає адресу того регіону, який ближчий до резолвера. Якщо регіон не проходить перевірку стану, DNS перестає повертати IP цього регіону, доки той не відновиться.

## Що знадобиться {#prereqs}

- Дві VM у різних регіонах, кожна за [плаваючим IP](/docs/api/floating-ips).
- Ваш застосунок, запущений на обох VM і готовий обслуговувати трафік.
- База даних або інше сховище зі станом, яке є в обох регіонах і реплікується між ними. Для Postgres підійде той самий примітив — [логічна реплікація, як під час міграції з RDS](/docs/guides/migrate-from-rds). Для Redis дзеркальте промахи кешу; для обʼєктного сховища використовуйте [міжрегіональну реплікацію](/docs/api/object-storage#cross-region).
- DNS-зона на DNS NimbusNexus (або в будь-якого DNS-провайдера, що підтримує набори записів із перевірками стану, — Route53, Cloudflare тощо).
- Ендпоінт перевірки стану, який справді перевіряє, що застосунок може обслуговувати трафік (а не просто повертає `200 OK` на `/healthz`).

```bash
export NIMBUS_KEY="nn_live_xxxxxxxxxxxxxxxx"
export ZONE_ID="zone_01HG7..."
export EAST_IP_ID="ip_01HG7Y3..."      # floating IP in us-east-1
export WEST_IP_ID="ip_01HG7Y4..."      # floating IP in eu-central-1
```

## 1 · Створіть набір записів із кількома значеннями {#record-set}

Додайте набір записів A з IP обох регіонів і маршрутизацією за затримкою:

```bash
EAST_IPV4=$(curl -s {{API_BASE_URL}}/v1/floating-ips/$EAST_IP_ID \
  -H "Authorization: Bearer $NIMBUS_KEY" | jq -r '.ipv4')

WEST_IPV4=$(curl -s {{API_BASE_URL}}/v1/floating-ips/$WEST_IP_ID \
  -H "Authorization: Bearer $NIMBUS_KEY" | jq -r '.ipv4')

curl -X POST {{API_BASE_URL}}/v1/dns/zones/$ZONE_ID/records \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"name\": \"app.example.com\",
    \"type\": \"A\",
    \"routing_policy\": \"latency\",
    \"ttl\": 60,
    \"values\": [
      { \"value\": \"$EAST_IPV4\", \"region\": \"us-east-1\" },
      { \"value\": \"$WEST_IPV4\", \"region\": \"eu-central-1\" }
    ]
  }"
```

Ключові поля:

- `routing_policy: 'latency'` — DNS-резолвери отримують IP, що відповідає географічно найближчому регіону. Альтернативи: `'weighted'` (розподіл у відсотках), `'failover'` (основний/резервний, ніколи не round-robin), `'geo'` (маршрутизація за країною клієнта).
- `ttl: 60` — TTL у 60 секунд. Нижчий TTL = швидший failover (резолвери раніше повторюють запит) ціною більшої кількості DNS-запитів. Для сервісу з високими вимогами до доступності 60 — правильне значення; для конфігурацій із нижчим SLA підійде 300.

## 2 · Додайте перевірки стану {#health-checks}

Кожне значення в наборі записів отримує перевірку стану. Невдалі перевірки виводять це значення з ротації:

```bash
curl -X POST {{API_BASE_URL}}/v1/dns/zones/$ZONE_ID/records/$RECORD_ID/health-checks \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "value_index": 0,
    "type": "https",
    "path": "/healthz",
    "expected_status": 200,
    "interval_seconds": 10,
    "failure_threshold": 3,
    "success_threshold": 2
  }'
```

Повторіть для `value_index: 1` (другий регіон). Що робить кожне поле:

- `interval_seconds: 10` — перевірка кожні 10 секунд.
- `failure_threshold: 3` — три невдачі поспіль, перш ніж значення вважатиметься недоступним. Разом з `interval_seconds` це 30 секунд до виключення регіону — трохи більше за поріг випадкових мережевих збоїв і значно менше, ніж «ми вже бачимо це в PagerDuty».
- `success_threshold: 2` — два успіхи поспіль, перш ніж значення знову вважатиметься доступним. Запобігає постійному перемиканню під час нестабільного відновлення.

Ендпоінт перевірки стану має значення. Не робіть так, щоб він безумовно виконував `return 200 OK`, — це зводить усю ідею нанівець. Нехай він справді перевіряє залежності (підключення до бази даних, кеш, чергу), щоб повертати помилку тоді, коли не працював би й застосунок.

## 3 · Протестуйте {#test}

Спровокуйте «збій», заблокувавши перевірки стану в одному регіоні:

```bash
# On the us-east-1 VM, drop traffic from the health-check source CIDR
sudo iptables -A INPUT -s <healthcheck-cidr> -j DROP
```

(CIDR, з яких надходять перевірки стану, повертає `GET /v1/dns/healthcheck-source-cidrs`.)

Протягом 30 секунд набір записів має перестати повертати IP us-east-1:

```bash
dig +short app.example.com
# Should return only the eu-central-1 IP for the next several seconds
```

Скасуйте правило iptables, щоб відновити регіон. Протягом 20 секунд (`2 * interval_seconds`) він має повернутися в ротацію.

## 4 · Реплікація бази даних {#db}

Рівень DNS вирішує, куди потрапляє трафік; з рівнем даних складніше. Патерни:

**Для навантажень переважно з читанням:**

- Головна БД в одному регіоні, read-репліка — в іншому.
- Застосунок читає з локального регіону (з репліки, якщо він у вторинному регіоні).
- Записи завжди йдуть на головний вузол (тому у вторинному регіоні затримка запису вища).
- У разі збою основного регіону: підвищте репліку до головного вузла й перемкніть читання та записи на новий головний вузол.

**Для навантажень з інтенсивним записом, що допускають multi-master:**

- Використовуйте базу даних із підтримкою реплікації active-active (CockroachDB, YugabyteDB).
- Обидва регіони читають і записують локально; конфлікти розвʼязує рушій.
- Складніше в експлуатації; виправдано, лише коли затримка запису з одним master — справжня проблема.

**Для кешу й черги:**

- Кеш: після failover розраховуйте на холодний кеш. Більшість застосунків відновлюються за кілька хвилин; удар по SLA прийнятний.
- Черга: тримайте окремі черги в кожному регіоні; застосунок виходить з того, що регіональна черга може бути недоступна, доки регіон не відновиться.

NimbusNexus поки не пропонує мультирегіональної бази даних active-active. Наразі керуйте реплікацією самостійно — через логічну реплікацію (Postgres), binlog (MySQL) або change streams (MongoDB).

## Чим це не є {#not}

- **Не failover active-active для стану**: записи все одно зосереджені на одному головному вузлі. Рівень DNS спрямовує користувачів; рівень бази даних здебільшого лишається з одним master.
- **Не прозоро для клієнтів**: TCP-зʼєднання з IP регіону, що відмовив, скидаються; клієнти перепідключаються (більшість HTTP-клієнтів із цим добре справляються; деяким клієнтам long-polling або SSE потрібен обробник повторів).
- **Не нульовий RTO**: 20–60 секунд — мінімум за TTL = 60. Нижчий TTL допомагає, але ціною більшого обсягу DNS-запитів.
