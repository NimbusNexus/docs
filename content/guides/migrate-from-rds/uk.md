# Міграція з AWS RDS

У цій інструкції продакшн-база даних Postgres або MySQL переїжджає з AWS RDS у керовані бази даних NimbusNexus за допомогою логічної реплікації. Схема така: масове копіювання наживо (без даунтайму), потокова передача поточних змін через WAL/binlog, а потім cutover із короткою паузою зʼєднань.

Очікуваний даунтайм: **~30 секунд** на cutover. Загальна тривалість залежить від обсягу даних (8–30 хвилин на початкове копіювання за типових обсягів).

Підходить для:

- Postgres 12+
- MySQL 8.0+

## Що знадобиться {#prereqs}

На боці AWS:

- В інстансі RDS має бути ввімкнена логічна реплікація (`rds.logical_replication = 1` для Postgres; `binlog_format = ROW` для MySQL).
- Користувач із правами на реплікацію (або можна використати головного користувача).
- Вхідний мережевий доступ з IP NimbusNexus (конкретні CIDR ми отримаємо трохи далі).
- Свіжий бекап інстансу RDS. Про всяк випадок.

На боці NimbusNexus:

- API-ключ.
- Обраний регіон. Затримка між хостом міграції та вихідним інстансом RDS має значення — виберіть регіон, найближчий до регіону RDS (напр., `us-east-1` для RDS у `us-east-1`).

```bash
export NIMBUS_KEY="nn_live_xxxxxxxxxxxxxxxx"
export REGION="us-east-1"
```

## 1 · Розгорніть цільовий кластер {#provision}

Створіть цільовий кластер із тим самим рушієм і версією, що й у джерела:

```bash
curl -X POST {{API_BASE_URL}}/v1/databases \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "app-prod-migrated",
    "engine": "postgres",
    "engine_version": "16",
    "tier": "production-4-16",
    "region": "us-east-1",
    "high_availability": true,
    "tls_required": true
  }'
```

Підберіть клас інстансу якомога ближчий до вихідного. Якщо взяти значно менший, цільовий кластер може відставати на етапі потокової передачі WAL/binlog. Змінити розмір можна після завершення міграції.

Збережіть ідентифікатор кластера:

```bash
export DB_ID="db_01HG7..."
```

Дочекайтеся `state: running` (4–7 хвилин).

## 2 · Додайте IP NimbusNexus до списку дозволених на RDS {#allowlist}

Отримайте CIDR вихідного трафіку наших воркерів міграції у вашому регіоні:

```bash
curl {{API_BASE_URL}}/v1/databases/migration-source-cidrs?region=us-east-1 \
  -H "Authorization: Bearer $NIMBUS_KEY"
```

Відповідь — це список блоків `/24`. Додайте їх до вхідних правил групи безпеки RDS на порту Postgres або MySQL. Обмежте доступ лише цими CIDR — не відкривайте `0.0.0.0/0`.

## 3 · Запустіть міграцію {#kick-off}

```bash
curl -X POST {{API_BASE_URL}}/v1/databases/$DB_ID/migrate \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "source": {
      "host": "mydb.abc123.us-east-1.rds.amazonaws.com",
      "port": 5432,
      "database": "app",
      "username": "migration_user",
      "password": "••••",
      "tls_required": true
    },
    "mode": "logical-replication"
  }'
```

Відповідь містить `migration_id`:

```bash
export MIG_ID="mig_01HG7Y3..."
```

Міграція проходить три фази, які API явно показує:

1. **`copying`** — масове копіювання. Читає кожен рядок із джерела й записує в цільовий кластер. Займає більшу частину часу. Джерело тим часом повністю працездатне; читання й записи тривають у звичайному режимі.
2. **`streaming`** — коли копіювання завершено, цільовий кластер починає стежити за WAL (Postgres) або binlog (MySQL) джерела. Відставання на цьому етапі зазвичай < 1 секунди.
3. **`cutover-ready`** — копіювання завершено, потік наздогнав джерело. Можна робити cutover.

## 4 · Стежте за прогресом {#progress}

```bash
while true; do
  curl -s {{API_BASE_URL}}/v1/databases/migrations/$MIG_ID \
    -H "Authorization: Bearer $NIMBUS_KEY" \
    | jq '{ phase, rows_copied, rows_total, lag_seconds }'
  sleep 30
done
```

Чого чекати:

- `phase: 'copying'` → `phase: 'streaming'` (початкове копіювання завершено)
- `lag_seconds` знижується до 0–2 (відставання наздогнано)
- `phase: 'cutover-ready'` (можна робити cutover)

Для великих баз даних (~100 GB+) підпишіться на [вебхук `database.migration.cutover_ready`](/docs/webhooks#events), щоб отримати сповіщення, коли настане час.

## 5 · Cutover {#cutover}

Коли міграція досягла `cutover-ready`, вікно cutover виглядає так:

1. **Призупиніть записи в джерело.** Зупиніть застосунок або переведіть інстанс RDS у режим лише для читання. Критичний крок — усе, що запишеться в джерело після цього моменту, не потрапить у цільовий кластер.
2. **Дочекайтеся `lag_seconds: 0`.** Це має статися майже миттєво, бо записи призупинено.
3. **Зробіть цільовий кластер головним:**

   ```bash
   curl -X POST {{API_BASE_URL}}/v1/databases/migrations/$MIG_ID/cut-over \
     -H "Authorization: Bearer $NIMBUS_KEY"
   ```

4. **Перенаправте застосунок на новий рядок підключення.** Візьміть новий рядок підключення з `GET /v1/databases/$DB_ID/connection`.
5. **Відновіть трафік.** Тепер застосунок записує в новий кластер.

Загалом кроки 1–5 зазвичай займають 20–40 секунд.

Виклик, що робить цільовий кластер головним, водночас є кроком підтвердження — доки ви його не зробите, цільовий кластер і далі стежить за джерелом. Тож якщо посеред cutover щось піде не так, головним лишається вихідний інстанс RDS; просто відновіть трафік на нього. Міграцію можна перезапустити будь-коли.

## 6 · Перевірте результат {#verify}

Після cutover виконайте швидкий запит для перевірки:

```bash
psql "postgresql://app:••••@{{DB_HOST_DEMO}}:5432/app?sslmode=verify-full" \
  -c "SELECT count(*) FROM users;"
```

Порівняйте кількості з даними, які ви записали до міграції. Вибірково перевірте кілька рядків.

## 7 · Видаліть завдання міграції й виведіть RDS з експлуатації {#cleanup}

```bash
curl -X DELETE {{API_BASE_URL}}/v1/databases/migrations/$MIG_ID \
  -H "Authorization: Bearer $NIMBUS_KEY"
```

Завдання міграції перестає стежити за джерелом і звільняє свої ресурси. Цільовий кластер працює далі у звичайному режимі; зникає лише інфраструктура міграції.

Виведіть RDS з експлуатації на боці AWS — спершу снапшот, потім видалення інстансу. Зберігайте снапшот тиждень як страховку.

## Типові пастки {#gotchas}

- **Розсинхронізовані послідовності.** Логічна реплікація Postgres не реплікує просування послідовностей. Після cutover виконайте `SELECT pg_catalog.setval(seq_name, max(id)) FROM ...` для кожної послідовності, щоб просунути її за максимальне значення у відповідній таблиці.
- **Ролі й дозволи не реплікуються.** Створіть їх заново в цільовому кластері до cutover. Використайте `pg_dumpall --roles-only` (Postgres) або аналог.
- **Розширення не реплікуються.** Якщо джерело використовує `pgvector`, `postgis` тощо, увімкніть їх у цільовому кластері до початку міграції.
- **Не забудьте про історію `pg_stat_statements`.** Логічна реплікація її не копіює. Після cutover виконайте `SELECT pg_stat_statements_reset()` у цільовому кластері, щоб моніторинг бачив чисту базову лінію.
