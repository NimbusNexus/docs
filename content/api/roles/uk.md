# Ролі

Роль — це набір дозволів. **Призначення ролі** — це надання ролі користувачу в проєкті. Той самий користувач може мати різні ролі в різних проєктах; користувач без ролі в проєкті взагалі його не бачить.

## Вбудовані ролі {#built-in}

Кожен проєкт має чотири вбудовані ролі, які можна призначати, не визначаючи нічого власного:

| Роль | Що може робити |
| --- | --- |
| **`viewer`** | Читати всі ресурси. Жодного запису, жодного видалення. Підходить для інструментів моніторингу, аудиторів. |
| **`editor`** | Створювати + оновлювати більшість ресурсів. Не може керувати IAM (користувачами, ролями, ключами). Підходить для розробників у щоденній роботі. |
| **`admin`** | Усе, що може `editor`, плюс IAM. Може створювати користувачів, надавати/відкликати ролі, керувати API-ключами. |
| **`billing-admin`** | Читати рахунки, змінювати спосіб оплати, переглядати + підвищувати квоти. Без доступу до ресурсів. Підходить для фінансового відділу. |

Роль `admin` **не** включає `billing-admin`, і навпаки. Так задумано: інженер, який працює з API, не має бути тим самим, хто затверджує рахунок.

## Деталізовані ролі {#granular}

Окрім чотирьох вбудованих ролей, ми надаємо деталізовані ролі для окремих ресурсів — для випадків, коли `editor` дає забагато:

- `vms:operator` — лише створювати / запускати / зупиняти / видаляти VM, без мережі
- `storage:operator` — керувати томами, bucket-ами, снапшотами, бекапами
- `dns:admin` — повне керування DNS-зонами + записами; більше нічого
- `networking:admin` — мережі, підмережі, групи безпеки, плаваючі IP, LB
- `databases:admin` — керовані бази даних + їхні бекапи

Їх призначають так само, як і вбудовані, через `POST /v1/role-assignments`.

## Власні ролі {#custom}

Визначайте власні ролі через `POST /v1/roles` (у мінімальному прикладі нижче цього немає), перелічуючи дозволи, які треба обʼєднати. Назви дозволів мають формат `<resource>:<action>` — напр., `vms:read`, `volumes:create`, `databases:snapshot`. Повний каталог дозволів доступний через `GET /v1/permissions`.

Сценарії для власних ролей: «читати все, крім білінгу» для аудитора безпеки; «керувати DNS-записами, але не зонами» для маркетингової команди, яка відповідає за вміст піддоменів, але не за делегування зони.

## Як поєднуються призначення ролей {#compose}

Користувач може мати кілька призначень ролей в одному проєкті. Ефективний набір дозволів — це **обʼєднання**: ролі додаються, а не перемножуються. Якщо надати одному користувачу `viewer` + `vms:operator`, він отримає читання всього + запис саме для VM.

Відкликання однієї ролі не відкликає інших. Щоб повністю позбавити користувача прав, видаліть кожне призначення по одному або видаліть користувача (це атомарно відкликає всі призначення).
