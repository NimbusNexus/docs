# Снапшоти

Снапшот — це копія вихідного ресурсу (VM, блокового тому або керованої бази даних) на певний момент часу, записана в обʼєктне сховище. Снапшоти переживають своє джерело: видалення VM не видаляє її снапшотів. Відновлення зі снапшота створює **новий** ресурс; оригінал ніколи не змінюється.

## Три типи джерел {#source-kinds}

| Тип джерела | Що фіксується | Ціль відновлення |
| --- | --- | --- |
| `vm` | Стан кореневого диска + підʼєднаних томів в узгоджений момент | Нова VM такого самого або більшого розміру, у будь-якому регіоні |
| `volume` | Вміст блокового тому в узгоджений момент | Новий блоковий том такого самого або більшого розміру, будь-який регіон |
| `database` | Логічний снапшот на рівні рушія (межа WAL у Postgres / MySQL, точка oplog у MongoDB тощо) | Нова база даних із тим самим рушієм + версією |

Поле `source_kind` снапшота показує, який це тип; ендпоінт відновлення на основі цього поля передає запит потрібному бекенду.

## Як забезпечується узгодженість снапшота {#consistency}

- **Снапшоти томів** призупиняють чергу вводу-виводу, роблять снапшот на блоковому рівні (~10 секунд) і продовжують копіювання у фоновому режимі. VM продовжує працювати; записи, що надходять після точки снапшота, потрапляють у стан після снапшота.
- **Снапшоти VM** атомарно знімають снапшот кореневого диска + кожного підʼєднаного тому. Якщо ви налаштували хуки до/після снапшота (скрипти cloud-init, що скидають буфери застосунку), вони виконуються в процесі створення снапшота.
- **Снапшоти баз даних** використовують нативний механізм узгодженості рушія. Призупиняти ввід-вивід на боці клієнта не потрібно; власна межа журналу комітів бази даних гарантує, що ви зможете відновитися до транзакційно узгодженої точки.

Для застосунків, яким потрібна узгодженість на рівні застосунку (напр., база даних Postgres, розміщена на VM, а не в керованих базах даних), краще використовувати власний API снапшотів бази даних, а не снапшот тому.

## Сховище + строк зберігання {#storage}

Снапшоти зберігаються на холодному рівні (\$0,04/GB·міс, з дедуплікацією відносно попередніх снапшотів того самого джерела). Строк зберігання за замовчуванням — **7 днів**; щоб подовжити його до 365 днів, передайте `retention_days` під час створення.

Завдяки дедуплікації серія щоденних снапшотів однієї VM займає приблизно стільки, скільки сама VM, плюс щоденні зміни, — а не N× розміру VM. В усталеному стані політика «щоденний снапшот, зберігання 30 днів» для VM на 100 GB зазвичай коштує як 130–160 GB загалом, залежно від обсягу змін.

## Семантика відновлення {#restore}

Відновлення створює зі снапшота **новий ресурс**. Вихідний ресурс (якщо він ще існує) не зачіпається. Відновлені VM отримують новий ідентифікатор, новий IP і нові SSH-ключі з поточних ключів проєкту (початковий набір ключів не зберігається — якщо відновити стару VM після ротації ключів, ви отримаєте VM, до яких старі, видалені ключі не мають доступу).

Міжрегіональне відновлення підтримується. Внутрішня передача даних для копії снапшота першого разу тарифікується як міжрегіональний egress (\$0,005/GB); подальші відновлення в цільовому регіоні не повторюють передачі.
