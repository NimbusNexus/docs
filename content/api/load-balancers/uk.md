# Балансувальники навантаження

Балансувальник навантаження стоїть перед парком VM з єдиним VIP (віртуальним IP), розподіляє трафік між бекендами й автоматично виводить несправні з ротації. Прослуховувач працює за протоколом `TCP`, `UDP`, `SCTP`, `HTTP`, `HTTPS`, `TERMINATED_HTTPS` або `PROMETHEUS` і надсилає весь свій трафік у свій пул за замовчуванням; правил маршрутизації за шляхом чи заголовками немає.

## Чотири вкладені ресурси {#sub-resources}

Сам балансувальник навантаження — це контейнер; логіка маршрутизації міститься у вкладених ресурсах:

- **Прослуховувач** — по одному на кожну пару (протокол, порт), на якій LB приймає трафік. `HTTPS:443` — один прослуховувач; `HTTP:80` — інший. Один LB може мати багато прослуховувачів.
- **Пул** — група бекендів, привʼязана до одного прослуховувача (`listener_id`) або до балансувальника навантаження (`loadbalancer_id`). Кожен пул має `protocol` (`HTTP`, `HTTPS`, `TCP`, `UDP`, `SCTP`, `PROXY` або `PROXYV2`) і `lb_algorithm`: `ROUND_ROBIN`, `LEAST_CONNECTIONS`, `SOURCE_IP` або `SOURCE_IP_PORT`. Налаштування збереження сесій немає.
- **Учасник пулу** — один бекенд у пулі: IP-адреса в `address` і `protocol_port`, а також вага `weight` (0–256, за замовчуванням 1).
- **Монітор стану** — активна перевірка стану для кожного пулу. Учасників, що не пройшли перевірку, виводять із ротації, доки вони не відновляться.

Кожен із них має власні ендпоінти, наведені нижче: `/api/v1/loadbalancers/`, `/api/v1/listeners/`, `/api/v1/pools/`, `/api/v1/pools/{pool_id}/members/` і `/api/v1/health_monitors/`.

## Термінація SSL {#ssl}

Для прослуховувачів HTTPS є два варіанти:

- **TLS термінується на LB.** Використайте прослуховувач `TERMINATED_HTTPS` і вкажіть у `default_tls_container_ref` (і в `sni_container_refs` — для додаткових сертифікатів) наявний контейнер сертифікатів. LB обслуговує TLS для клієнтів, а з вашими VM спілкується відкритим текстом. Цей API не завантажує й не випускає сертифікатів.
- **Наскрізний TLS.** LB лише пересилає TCP на рівні L4; TLS обробляють ваші VM. Потрібно, коли бекенд має бачити оригінальний сертифікат клієнта. Використайте прослуховувач `HTTPS` або `TCP`.

## Перевірки стану {#health-checks}

Монітор стану перевіряє кожного учасника кожні `delay` секунд і чекає на відповідь `timeout` секунд (менше за `delay`); обидва значення задаєте ви. Його `type` — це `HTTP`, `HTTPS`, `PING`, `TCP`, `TLS-HELLO`, `UDP-CONNECT` або `SCTP`. `GET /api/v1/loadbalancers/{loadbalancer_id}/status` показує `operating_status` кожного учасника.

- Учасника виводять із ротації після `max_retries_down` невдалих перевірок (3, якщо не задати).
- Він повертається в ротацію після `max_retries` успішних перевірок; це значення потрібно задати обовʼязково.

Для перевірок HTTP і HTTPS задайте `url_path`, `http_method` і `expected_codes`. Спрямуйте `url_path` на щось у своєму застосунку, що швидко повертає відповідь, — і не змушуйте перевірку виконувати реальну роботу, інакше сама перевірка стане навантаженням.
