# Керовані бази даних

NimbusNexus запускає шість рушіїв баз даних як керовані сервіси. Операційну роботу — failover, бекапи, оновлення мінорних версій, патчі ОС — ми беремо на себе, а ви отримуєте рядок підключення й нативний протокол рушія на іншому боці. **Жодного пропрієтарного формату передачі даних, жодної спеціальної клієнтської бібліотеки**: підключайтеся через `psql`, `mongo`, офіційний клієнт Kafka тощо.

## Рушії {#engines}

| Рушій | Для чого | Початковий розмір |
| --- | --- | --- |
| `postgres` | Транзакційне навантаження, безпечний вибір за замовчуванням для «мені потрібна база даних». | `db-1-4` |
| `mysql` | Коли застосунок або команда вже працюють на MySQL. Для нових розробок правильний вибір за замовчуванням — PostgreSQL. | `db-1-4` |
| `mongodb` | Документне навантаження, динамічні схеми, семантика replica set. | `db-2-8` |
| `redis` | Кеш, сховище сесій, pub/sub, черги. Без SQL. | `db-1-2` |
| `kafka` | Потокова передача подій, агрегація логів, надійний pub/sub. Мінімум три брокери. | `db-2-8` × 3 |
| `opensearch` | Повнотекстовий пошук, аналітика логів. | `db-4-16` |

Коди розмірів дотримуються тієї самої схеми, що й для VM (`db-<vCPU>-<RAM_GB>`), з окремим ціновим множником для кожного рушія: Redis дешевший за Postgres на тому самому обладнанні, бо в нього немає WAL на диску; MongoDB дорожчий через накладні витрати на ліцензування replica set.

## Життєвий цикл {#lifecycle}

База даних проходить через пʼять станів:

- `provisioning` — інстанс(и) запускаються. 60–120 секунд для одновузлових рушіїв (Postgres, MySQL, Redis), 90–180 секунд для реплікованих (MongoDB, Kafka, OpenSearch).
- `running` — приймає підключення за опублікованим рядком підключення.
- `maintenance` — застосовується мінорне оновлення або патч. Зʼєднання зберігаються; під час cutover база даних ненадовго недоступна (зазвичай <5 секунд для Postgres/MySQL, довше для Kafka).
- `stopping` → `stopped` — призупинено. Плата за обчислення припиняється; зберігання й далі тарифікується. Запустити знову можна будь-коли.
- `terminated` — видалено.

Стан повертається в кожній відповіді на GET у полі `state`. Тривалі переходи (початкове розгортання, оновлення версії) повідомляють про прогрес у вкладеному обʼєкті `operation` — див. сторінку [Угоди](/docs/conventions).

## Бекапи й снапшоти {#backups}

Паралельно працюють два механізми бекапу:

- **Безперервний бекап WAL** (лише Postgres, MySQL). Увімкнено за замовчуванням. Ми надсилаємо журнал попереднього запису в обʼєктне сховище кожні ~5 секунд і можемо відновити базу на будь-який момент за останні 7 днів. **Відновлення на момент часу**.
- **Снапшоти на вимогу** (усі рушії). Запускаються викликом `POST /v1/databases/{id}/snapshots`. Узгоджені (призупиняти ввід-вивід не потрібно), зберігаються в обʼєктному сховищі, відновлюються в нову базу даних у тому самому регіоні.

Снапшоти не залежать від вихідної бази даних: якщо видалити джерело, снапшоти збережуться. Строк зберігання за замовчуванням — 7 днів; збільште його в дашборді або передавши `retention_days` у запиті на снапшот.

## Підключення {#connections}

Відповідь на GET для кожної бази даних містить обʼєкт `connection`:

```json
{
  "connection": {
    "host": "{{DB_HOST_DEMO}}",
    "port": 5432,
    "database": "main",
    "username": "nimbus",
    "password_secret": "secret://projects/.../database-passwords/db_01H8FZ...",
    "ssl": "require"
  }
}
```

Пароль передається як посилання на секрет у вигляді URL, а не вбудовується напряму: отримайте його через `GET /v1/secrets/{secret-id}` і кешуйте на час життя зʼєднання. Так значення паролів не потрапляють у логи, які фіксують повні записи баз даних.

Усі бази даних вимагають TLS для клієнтських підключень. Самопідписані сертифікати не приймаються; набір сертифікатів CA ми публікуємо за адресою `/v1/databases/ca-bundle.pem`. Клієнтам Postgres / MySQL слід використовувати `sslmode=verify-full` і вказати в `sslrootcert` цей набір.

## Версії та оновлення {#versions}

- **Мінорні версії** застосовуються автоматично під час щотижневого вікна обслуговування (неділя 02:00–04:00 за часом регіону бази даних, налаштовується). Без даунтайму для Postgres/MySQL з безперервним WAL; рушії з replica set проходять короткий failover.
- **Мажорні версії** потребують явного виклику `POST /v1/databases/{id}/upgrade`. Перш ніж перемкнути головний вузол, ми тестуємо оновлення на ваших даних на снапшоті, тож невдале оновлення означає відкат, а не пошкодження даних.

Мажорні версії підтримуються щонайменше 24 місяці після релізу в upstream. Графіки завершення підтримки ми публікуємо в журналі змін щонайменше за 90 днів.

## Примітки щодо цін {#pricing}

- Обчислення: посекундно, за еквівалент vCPU, з множником рушія (див. [сторінку цін]({{BASE_URL}}/managed-databases)).
- Зберігання: \$0,18/GB·міс (Performance NVMe, за замовчуванням).
- Бекапи: \$0,04/GB·міс за рівень снапшотів.
- Міжрегіональна реплікація (там, де підтримується): тарифікується як стандартний міжрегіональний egress (\$0,005/GB).
- Жодної плати за підключення, жодної плати за IOPS, жодної плати за події failover.

Базова стартова ціна — \$19/міс за Postgres `db-1-4` у Вірджинії: це інстанс 1 vCPU / 4 GB / 50 GB, найменший розмір, який має сенс для продакшн-навантажень.
