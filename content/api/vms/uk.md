# Віртуальні машини

Віртуальна машина NimbusNexus — це обчислювальний інстанс з обліком використання (одне дерево процесів, один мережевий інтерфейс, один кореневий диск), який тарифікується посекундно. Щоб створити VM, оберіть розмір і регіон; усе інше (блокові томи, публічні IP, снапшоти) підʼєднується до неї як окремі ресурси.

## Коли використовувати VM {#when-to-use}

VM — правильний примітив, коли вам потрібні:

- Постійний стан на диску між запитами (база даних, кеш збірок, тривалий воркер черги).
- Повний контроль над ОС — встановлення пакетів, налаштування параметрів ядра, запуск будь-чого, що потребує системного доступу.
- Конкретна конфігурація інстансу — з великим обсягом памʼяті для аналітичного навантаження, з GPU для інференсу, оптимізована для обчислень для сервісу, обмеженого CPU.

Якщо ваше навантаження **не має стану й складається із запитів**, зазвичай краще підходять контейнерні платформи (керовані сервіси Kubernetes, serverless-середовища виконання). Межа приблизно така: якщо вас засмутить, що перезапуск процесу стер локальні файли, вам потрібна VM.

## Розміри, сімейства, іменування {#sizes}

Розміри мають формат `<family>-<vCPU>-<RAM_GB>`. Зараз є три сімейства:

- `gp-*` — загального призначення. Збалансовані CPU + RAM. З нього починає більшість навантажень.
- `co-*` — оптимізоване для обчислень. 2× CPU на долар порівняно з `gp`, удвічі менше RAM на долар.
- `mo-*` — оптимізоване для памʼяті. Зворотний компроміс. Підходить для кешів у памʼяті, купи JVM, проміжних даних аналітики.

Тобто `gp-4-16` — це 4 vCPU, 16 GB RAM, загального призначення. `co-16-32` — 16 vCPU, 32 GB RAM, оптимізований для обчислень. Повний список доступний через `GET /v1/vms/sizes` (у цьому довіднику він ще не генерується автоматично — незабаром).

## Життєвий цикл {#lifecycle}

VM проходить через такі стани:

- `provisioning` — диск готується, а гіпервізор виділяє інстанс. ~5–30 секунд для кешованого образу, до 90 секунд, якщо образ завантажується вперше.
- `running` — завантаження завершено, інстанс приймає трафік. Це усталений стан, у якому VM проводить більшість часу.
- `stopping` → `stopped` — коректне вимкнення. VM зберігається; плата за обчислення припиняється, але плата за зберігання нараховується й далі.
- `terminated` — VM видалено. Підʼєднані блокові томи або теж видалено (за замовчуванням), або відʼєднано, і вони залишаються доступними (якщо під час видалення було встановлено `preserve_volumes: true`).

Переходи станів повертаються в полі `state` у кожній відповіді на `GET`. Тривалі переходи повідомляють про прогрес у вкладеному обʼєкті `operation` — патерн опитування операцій, який використовується тут і в решті API, описано на сторінці [Угоди](/docs/conventions).

## Імена й стабільні ідентифікатори {#ids}

Кожна VM має два ідентифікатори:

- `id` — непрозорий, з префіксом `vm_` і 26-символьним суфіксом у base32. Стабільний протягом усього життя VM. Використовуйте його в URL, зовнішніх ключах, журналах аудиту.
- `name` — зрозуміле людині, 1–63 символи, літери й цифри + дефіси, унікальне в межах проєкту. Змінюється через `PUT /v1/vms/{id}`. Не використовуйте його в коді, який не хочете переписувати того дня, коли хтось перейменує VM.

Довідник ендпоінтів нижче використовує `{id}` у шаблонах шляхів; ви передаєте непрозорий ідентифікатор.
