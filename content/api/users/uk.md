# Користувачі

Користувач — це ідентичність усередині [проєкту](/docs/api/projects). Користувачі мають ролі (які надають дозволи), можуть генерувати API-ключі (привʼязані до користувача) і можуть використовувати довіри, щоб діяти від імені інших проєктів.

## Користувач ≠ обліковий запис для входу {#identity-model}

«Користувач» у цьому API — це **запис ідентичності**, а не людина. Та сама людина може бути:

- Одним користувачем у `prod` (продакшн-проєкт)
- Іншим користувачем у `staging` (окремий запис ідентичності, та сама електронна адреса)
- Третім користувачем у `dev`

Кожен користувач повністю ізольований від інших — у нього власні призначення ролей, власні API-ключі, власний журнал аудиту. Саме на цю межу ізоляції проєктів ми спираємося, щоб обмежити радіус ураження: скомпрометований користувач `dev` не може зачепити продакшн-ресурси, бо там його буквально не існує як ідентичності.

Якщо організація хоче, щоб одна людина мала одну ідентичність в усіх проєктах, налаштуйте федерацію через SAML/OIDC: ідентичність, яку надає SSO, стає тим самим користувачем в усіх проєктах, зіставлених правилами IdP. Це функція рівня enterprise; акаунти базового рівня використовують описану вище модель з окремими користувачами в кожному проєкті.

## Що можна робити з користувачем {#actions}

- **Створити** — створити нового користувача в проєкті того, хто здійснює виклик. Потрібен `iam:write` у цьому проєкті.
- **Отримати** — прочитати запис користувача. Достатньо `iam:read`.
- **Оновити** — змінити імʼя, опис, прапорець увімкнення. Деякі поля (напр., email) після створення змінити не можна; якщо спробувати, API поверне 400.
- **Видалити** — видалити назавжди. Усі призначення ролей і API-ключі користувача атомарно відкликаються.

Окремої дії «вимкнути», відмінної від «видалити», немає. Якщо потрібне мʼяке вимкнення (зберегти історію аудиту, заборонити вхід), встановіть `enabled: false` через оновлення — це і є шлях мʼякого вимкнення. Видалення — це остаточне видалення + відкликання всього.

## Чого робити не можна {#cant-do}

- **Переносити користувача між проєктами.** Створіть нового користувача в цільовому проєкті, скопіюйте потрібні надання ролей і видаліть старого.
- **Встановлювати пароль через API.** Паролі встановлюються лише через процедуру скидання пароля; API ніколи не приймає пароль відкритим текстом. Користувачі з SSO узагалі обходяться без паролів.
- **Отримувати список користувачів проєкту, у якому у вас немає призначених ролей.** Ізоляція проєктів жорстка — жодного перелічування між проєктами.
