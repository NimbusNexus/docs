# Бекапи

Бекапи — це керовані копії VM, томів і баз даних, які зберігаються на рівні холодного сховища з дедуплікацією та налаштовуваним строком зберігання. Ендпоінти підтримують як бекапи **на вимогу** (разові, ви викликаєте POST), так і **заплановані** бекапи (регулярні, їх запускає політика, привʼязана до вихідного ресурсу).

## Бекапи чи снапшоти {#backups-vs-snapshots}

І те, і інше — копії на певний момент часу; різняться вони тим, як працюють:

| | Снапшот | Бекап |
| --- | --- | --- |
| Створюється | Лише прямим викликом API | Прямим викликом АБО регулярною політикою |
| Зберігання | За замовчуванням 7 днів, подовжується вручну | Визначається явною політикою зберігання (щоденні/щотижневі/щомісячні рівні) |
| Ціна | \$0,04/GB·міс (холодний рівень, з дедуплікацією) | \$0,04/GB·міс + плата за отримання даних за кожне відновлення |
| Міжрегіональна реплікація | Вручну: відновлення, потім копіювання | Вбудована в політику |
| Відновлення як новий ресурс | Так | Так |
| Журнал аудиту | Стандартний | Стандартний + метадані про те, яка політика створила бекап |

Використовуйте снапшоти для разових копій, якими користуватиметеся самі. Використовуйте бекапи для регулярного сценарію «у нас завжди є копія 7-денної, 30-денної та 365-денної давності» — саме такий сценарій і реалізують політики.

## Бекапи за політиками {#policies}

Привʼяжіть політику бекапів до VM / тому / бази даних ось так:

```json
{
  "source_id": "vm_01H...",
  "source_kind": "vm",
  "schedule": "daily",
  "retention": {
    "daily": 7,
    "weekly": 4,
    "monthly": 12,
    "yearly": 5
  }
}
```

Ця політика в усталеному стані підтримує 7 щоденних + 4 щотижневі + 12 щомісячних + 5 щорічних = 28 активних бекапів. Старіші бекапи видаляються автоматично, коли минає їхній строк; прибирати їх вручну не треба.

Ендпоінти політик розташовані за адресою `/v1/backups/policies` (у мінімальному прикладі нижче їх немає — повний довідник див. в актуальній специфікації).

## Блокування на строк зберігання {#retention}

Бекап, на який поширюється активний рівень зберігання (напр., «щоденні, зберігати 7»), на цей період **заблокований від видалення**. Спроба видалити його до закінчення строку повертає 409. Це функція для відповідності вимогам: користувач не може видалити бекап, який ще перебуває у вікні зберігання, навіть якщо має права адміністратора.

Щоб обійти блокування, треба відʼєднати джерело від політики (бекап стає «осиротілим» і більше не заблокований на строк зберігання), а потім видалити бекап. Те, що бекап став «осиротілим», фіксується в журналі аудиту.

## Міжрегіональна реплікація {#cross-region}

Політика може задавати вторинний регіон: кожен бекап, створений політикою, реплікується у вторинний регіон протягом ~10 хвилин після створення. Реплікована копія тарифікується як міжрегіональне зберігання (на \$0,005/GB·міс дорожче, ніж в основному регіоні).

Відновлення з вторинного регіону не потребує жодних додаткових церемоній: `POST /v1/backups/{id}/restore` з ідентифікатором вторинної копії, а цільовим регіоном за замовчуванням буде регіон вторинної копії. Типове навчання з аварійного відновлення: щомісячне відновлення з вторинної копії в проєкт-пісочницю, перевірка, видалення.
