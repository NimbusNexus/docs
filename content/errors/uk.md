# Помилки

Кожна відповідь із помилкою від API Webhooks, Inboxes і Request Bins має той самий формат JSON. Щоб обробити кожен випадок, розгалужуйте обробку за `error.code` або за `error.next_code`, якщо помилка його містить. Не розбирайте `message` і не вирішуйте лише за статусом: один статус може мати кілька кодів, а `402` у кожному API має чотири.

> **Оновлено 2026-10-16.** У Webhooks назва користувацького заголовка, яка є дійсним HTTP-токеном з одним символом переведення рядка в кінці, тепер відхиляється так само, як будь-яка інша назва, що не є дійсним HTTP-токеном: `webhooks.custom_header_name_invalid` з `msg` цього правила й без `params` ([Валідація запиту](#codes-validation)). Раніше символ переведення рядка проходив перевірку токена, і назву відхиляли як керувальний символ, з `params.header`: як `webhooks.custom_header_control_character` з 2026-10-15 і як `value_error` до того. Запит, як і раніше, — `422` `validation_error`, і більше нічого не змінилося.
>
> **Оновлено 2026-10-15.** До запуску v1 усі перейменування, що тривали в Inboxes і Webhooks, завершено: помилка, яка мала `next_code`, тепер має цей код зі статусом цього коду, і жоден з двох API більше не надсилає `next_code`.
>
> - Запит, що не проходить валідацію, в обох API — це `validation_error`, і статус лишається `422`. В Inboxes це був `invalid_request`; у Webhooks для поля, яке API перевіряє сам, це був `unprocessable`. В обох API `details` має вигляд `{"errors": [...]}`; у Webhooks це був просто список ([Валідація запиту](#codes-validation)).
> - Кожен `500` в обох API — це `internal_error` (у Webhooks це був `internal`).
> - В Inboxes API-ключ або токен, якого API не розпізнає або не може перевірити, — це `invalid_credential`, і статус лишається `401` (раніше `unauthorized`). Відсутні чи відкликані облікові дані або сесія входу, що завершилася, — як і раніше `unauthorized` з `details.reason`.
> - В Inboxes статус, який не має власного коду, отримує код цього статусу, як-от `bad_request` для `400` (раніше `error`).
> - У Webhooks `plan_violation` більше немає. Ліміт ендпоінтів — це `quota_exceeded` (`402`, `details.reason` `allocation`), `max_attempts` понад стелю плану — `422` `validation_error`, а джерело RabbitMQ на плані, нижчому за Pro, або вимкнення верифікації ендпоінтів на плані, який її вимагає (зараз такого плану немає), — `not_entitled` (`402`).
> - У Webhooks масовий реплей, у якого `from` пізніше за `to`, — це `422` `validation_error` із записом на `["body", "to"]`, а вже не `409` `conflict`.
> - Правила, які Webhooks перевіряє сам, — щодо користувацьких заголовків, затримок `retry_schedule`, полів брокера джерела RabbitMQ і назв планів — указують власний `type` запису замість `value_error`; `loc`, `msg` і `params` не змінилися ([Валідація запиту](#codes-validation)).
> - В Inboxes облікові дані, обмежені певними проєктами, відхиляються з `details.reason` `project_confined` (раніше `project`) ([Що містить `details`](#details)).
> - В Inboxes `details` містить лише ті ключі, які наводить ця сторінка. `quota_exceeded` більше не надсилає `max_inboxes`, `max_http_bins` чи `monthly_messages` (читайте `metric`, `limit`, `current` і `period`), `not_entitled` API читання більше не надсилає `plan`, а `rate_limited` для окремої скриньки більше не надсилає `inbox_id`.
>
> Жоден `message` не змінився, як і жоден статус, крім статусів двох відмов Webhooks, які стали `422`. Ці зміни внесено до запуску v1, тому на них не поширювався 12-місячний період, описаний у розділі [Коли код перейменовують](#renames); цей розділ зіставляє кожне старе написання з новим.
>
> **Оновлено 2026-10-05.** Тіла помилок отримали нові поля й не втратили жодного: `request_id` (те саме значення, що й у заголовку `X-Request-ID`), `reason` та іменовані значення в `details` у значно більшій кількості помилок, `params` у записах валідації, що мають числову межу, і `next_code` у помилці, код якої перейменовують. Жоден статус, `code` чи `message` не змінився. У Webhooks `conflict` називає зіткнення в `details.reason`, місячний `quota_exceeded` називає свої `metric`, `limit`, `current` і `period`, кожен `413` називає свій `limit`, а `plan_violation` містить `next_code`, яким він стане, з `details` цього коду ([Коли код перейменовують](#renames)). Розділ [Формат](#shape) описує кожне поле.
>
> **Виправлено 2026-10-05.** Попередні версії цієї сторінки наводили коди, статуси й поля, яких API ніколи не надсилали, серед них `validation_failed` (400), `rate_limit_exceeded`, `quota_exceeded` як 429 і `fields`. Код, що зіставляє відповіді з ними, ніколи нічого не знаходив. Ті версії також обіцяли `request_id` у кожному тілі ще до того, як API почали його надсилати; тепер тіла помилок його містять, усі без винятку з 2026-10-06 ([Ідентифікатор запиту](#request-id)). Розділ [Коди, які раніше наводила ця сторінка](#earlier-versions) зіставляє кожен із них з тим, що API надсилає насправді.

## Формат {#shape}

Ключ лише для читання, яким намагаються створити скриньку в Inboxes або ендпоінт у Webhooks, отримує від обох таку відповідь (відрізняється лише `request_id`):

```json
{
  "error": {
    "code": "forbidden",
    "message": "admin scope required",
    "details": {
      "reason": "scope",
      "required": "admin"
    },
    "request_id": "5f0c2e9a8b7d4c31a6e4f2b1d9c8e7a6"
  }
}
```

Request Bins відмовляє тому самому ключу лише для читання з тим самим кодом і статусом, але в його `details` названо не область дії, а роль, потрібну для дії: `"reason": "role"` і `"required": "member"`. Ключ має цю роль, якщо має область дії `admin`, — у консолі акаунта це **Read & write** ([Що містить `details`](#details)).

До пʼяти полів. `code`, `message` і `request_id` є в кожному тілі помилки, яке надсилають API, а `details` і `next_code` зʼявляються, коли їм є що сказати:

| Поле | Є завжди | Що це |
|---|---|---|
| `code` | Так | Стабільний машинозчитуваний рядок. Розгалужуйте обробку за ним або за `next_code`, якщо той є. |
| `message` | Так | Англійський текст для логів і звернень у підтримку. Не локалізується й не призначений для інтерфейсу кінцевого користувача. |
| `details` | Ні | Структурований контекст: `reason`, що уточнює код, і значення, які до нього належать, як-от `id`, якого не знайдено. У помилці валідації — вхідні дані, що не пройшли перевірку. Формат залежить від коду; у помилці валідації це `{"errors": [...]}`, список записів. Див. розділ [Що містить `details`](#details). |
| `request_id` | Так | Ідентифікатор цього запиту, те саме значення, що й у заголовку відповіді `X-Request-ID`. Записуйте його в логи й називайте підтримці; ніколи не розгалужуйте за ним обробку. Див. розділ [Ідентифікатор запиту](#request-id). |
| `next_code` | Ні | Надсилається лише під час перейменування коду: код, який ця помилка матиме, коли перейменування завершиться. Віддавайте йому перевагу над `code`. Зараз жоден код не перейменовують, тому жоден API його не надсилає. Див. розділ [Коли код перейменовують](#renames). |

До члена `error`, як і до будь-якої відповіді, можуть додаватися нові поля; ігноруйте ті, які не використовуєте ([Політика версіонування](/docs/versioning#forward-compat)).

### Що містить `details` {#details}

Вважайте кожен ключ у `details` необовʼязковим: читайте потрібні й ігноруйте решту. Якщо там є `reason`, це стабільний машинний рядок, що уточнює код: чому запит відхилено з `forbidden` або що саме не знайшов `not_found`. Поруч із ним — значення, потрібні цій причині, під фіксованими назвами. Деякі коди містять значення без причини, а багато помилок не мають `details` зовсім. Як і `code`, `details.reason` — відкритий рядок, а не enum: нові причини й нові коди — це [адитивні зміни](/docs/versioning#additive), тож тримайте гілку за замовчуванням для обох. У таблиці наведено те, що ви можете зустріти, викликаючи API сьогодні. У її стовпці **API** значення **Обидва** означає Webhooks і Inboxes, а Request Bins має власні рядки.

| `code` | API | `details.reason` | Інші ключі в `details` |
|---|---|---|---|
| `unauthorized` | Обидва | `missing`: облікові дані не надіслано. `revoked`: ключ або сесію відкликано. `invalid`: в Inboxes — сесія входу, яка не пройшла перевірку, зазвичай тому, що спливла; у Webhooks — вхідна подія на `POST /v1/ingest/{source_id}`, підпис якої не проходить перевірку. `no_workspace`, лише в Inboxes: облікові дані не привʼязані до робочого простору. | — |
| `unauthorized` | Request Bins | `missing`: облікові дані не надіслано. `revoked`: ключ або сесію відкликано. `invalid`: сесія входу, яка не пройшла перевірку, зазвичай тому, що спливла. `no_workspace`: сесія входу не привʼязана до робочого простору. | — |
| `forbidden` | Обидва | `scope`: область дії облікових даних цього не дозволяє. `project_confined`: облікові дані, обмежені певними проєктами, використано на маршруті, що відповідає за весь робочий простір; Inboxes поки не приймає облікових даних, обмежених проєктами, тому надсилає це на кожному маршруті. `csrf`: сесія браузера надіслала запит на запис без заголовка `X-CSRF`. `operator`: маршрут або поле в запиті призначені лише для операторів платформи. | `required`, у більшості відмов `scope`: область дії, з якою запит було б дозволено (`admin` в Inboxes; `admin`, `read` або `publish` у Webhooks) |
| `forbidden` | Webhooks | `role`: ваша роль — у робочому просторі чи в проєкті ресурсу, з яким ви працюєте, — занизька. `project`: облікові дані або людина, яка ними користується, не мають доступу до проєкту, названого в запиті. `product_not_enabled`: ваш доступ не охоплює Webhooks. `not_provisioned`: робочий простір ще не налаштовано для Webhooks. | `required`, для `role`: найнижча дозволена роль (`admin`) |
| `forbidden` | Request Bins | `role`: ваша роль або область дії вашого ключа цього не дозволяє. `project_confined`: гостьове місце або ключ, обмежений проєктом; Request Bins обслуговує цілі робочі простори, тому надсилає це на кожному маршруті. `product_not_enabled`: ваш робочий простір не додав Request Bins або ваш вхід його не охоплює. `csrf`: сесія браузера надіслала запит на запис без заголовка `X-CSRF`. `no_workspace`: облікові дані не привʼязані до робочого простору, як-от сервісний токен. | `required`, для `role`: `member`, щоб створити чи змінити bin, `admin`, щоб видалити чи очистити його. Для ключа обидва означають область дії `admin` (**Read & write**). |
| `not_found` | Обидва | Тип ресурсу. Inboxes: `inbox`, `message`, `workspace`. Webhooks: `endpoint`, `source`, `event`, `delivery`, `capture`, `event_type`, `operational_endpoint`, `project`, `workspace`, `user` і `default_project` (запит на запис, що не називає проєкту, у робочому просторі, де проєктів ще немає). | `id`: ідентифікатор, який ви запитали. Відсутній для `user` і `default_project`, де ви його не вказували, а також для шляху, якого взагалі не існує. |
| `not_found` | Request Bins | Тип ресурсу: `bin` або `request`. Bin, який видалено або строк дії якого сплив, — це `bin`. | `id`: ідентифікатор, який ви запитали. Відсутній для шляху, якого взагалі не існує. |
| `bad_request` | Webhooks | `project_required`: запит на запис, що не називає проєкту, з облікових даних, які мають доступ до кількох проєктів. | `projects`: проєкти, до яких мають доступ облікові дані |
| `conflict` | Webhooks | Яке саме зіткнення, як-от `event_type_exists` чи `idempotency_key_reuse`. У розділі [Конфлікти](#codes-state) наведено кожну причину й коли її надсилають. | Значення, потрібні цій причині, як-от `id` ендпоінта, доставки чи проєкту, якого стосується зіткнення; розділ [Конфлікти](#codes-state) перелічує їх для кожної причини |
| `quota_exceeded` | Обидва | `allocation`: стеля плану на кількість (Inboxes: адреси; Webhooks: ендпоінти). `period`: місячна стеля (Inboxes: повідомлення; Webhooks: доставки). | `metric` (`inboxes` або `messages` в Inboxes; `endpoints` або `deliveries` у Webhooks) і його `limit`; `current` для `allocation`, а також для `period` у Webhooks (доставки, використані до відхиленої публікації), якщо кількість вдалося прочитати; `period` для `period`: місяць в Inboxes (`YYYY-MM`), перший день розрахункового періоду у Webhooks (`YYYY-MM-DD`). Публікацію відхиляють, якщо її доставки вивели б кількість за межу `limit`, тому у Webhooks `current` може бути меншим за `limit`. |
| `quota_exceeded` | Request Bins | `allocation`: стеля плану на кількість bin-ів, у `POST /v1/bins`. Ніколи не `period`: коли місячні запити вичерпано, bin-и відповідають відправникам і нічого не записують, а жоден виклик API не відхиляється. | `metric` (`bins`), його `limit` і `current` |
| `not_entitled` | Обидва | — | `feature`: `read_api` або `optional_phrase_gate` в Inboxes; `rabbitmq_sources` або `optional_endpoint_verification` у Webhooks. Webhooks надсилає `optional_endpoint_verification` у відповідь на вимкнення верифікації ендпоінтів на плані, який її вимагає; зараз такого плану немає. |
| `not_entitled` | Request Bins | — | `feature`: `read_api`, читання перехоплених запитів з API-ключем на плані Free; `forwarding`, задання URL пересилання чи надсилання тесту на плані Free |
| `payload_too_large` | Обидва | — | `limit` у байтах, у кожному `413`. Inboxes також надсилає `size`, якщо API виміряв тіло. |
| `payload_too_large` | Request Bins | — | `limit` у байтах, у кожному `413` |
| `unknown_event_type` | Webhooks | — | `event_type`: назва, яку не зареєстровано |
| `invalid_payload` | Webhooks | `payload`: payload не відповідає схемі свого типу події. `schema_invalid`: схема, яку ви реєструєте, не є дійсною JSON Schema. | Для `payload`: `errors`, до 20 записів `{path, keyword, params}` (див. нижче), і `total` — скільки записів було до обрізання (довжина списку, якщо нічого не обрізано). Для `schema_invalid`: `path`, JSON Pointer у схемі на місце, де сталася помилка. |
| `schema_too_large` | Webhooks | `bytes`, `depth`, `members`, `enum_values` або `patterns`: межа, яку порушила схема | `limit`; для `bytes` ще й `size` (обидва в байтах) |
| `schema_pattern_unsafe` | Webhooks | `too_long`, `does_not_compile`, `empty_repeat`, `nested_quantifier`, `ambiguous_alternation` або `too_complex`: правило, яке порушив шаблон | `pattern`: шаблон повністю, хоча `message` скорочує довгий; `limit` (у символах) для `too_long` |
| `schema_ref_unsupported` | Webhooks | — | `ref`: віддалений `$ref`, який API не розвʼязуватиме |
| `provider_secret_required` | Webhooks | — | `provider`: `stripe`, `github` або `rabbitmq` |
| `broker_not_allowed` | Webhooks | Для вашого брокера — жодної, хоч би яке правило його відхилило (`not_system_broker` надсилається лише власному робочому простору платформи) | `host`: брокер у вигляді `host:port` |
| `rate_limited` | Обидва | `inbox_rate` (Inboxes): похвилинний ліміт однієї скриньки. Webhooks не надсилає причини. | `retry_after` у секундах, те саме число, що й у заголовку `Retry-After` (обидва API). Для `inbox_rate` в Inboxes також `rate_per_min`. |
| `rate_limited` | Request Bins | — | `retry_after`: через скільки секунд для bin-а буде дозволено наступне тестове надсилання |
| `unavailable` | Inboxes | `ingest_disabled`: приймання повідомлень вимкнено | — |
| `unavailable` | Request Bins | `forwarding_disabled`: пересилання вимкнено для всього сервісу. `forwarder_unavailable`: тест не було взято на надсилання протягом 3 секунд, тож нічого не надіслано. | — |

В `invalid_payload` кожен запис у `details.errors` указує, що і де не пройшло перевірку. `path` — JSON Pointer на значення, яке не пройшло перевірку: `""` — це сам payload, а для відсутнього чи неочікуваного члена він указує на обʼєкт, який мав би або не мав би його містити. `keyword` — ключове слово JSON Schema, вимогу якого не виконано (`required`, `type`, `enum`, `const`, `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `pattern`, `format` або `additionalProperties`), або `other` для будь-якого іншого ключового слова. `params` містить `property` (відсутній чи неочікуваний член, по одному запису на кожен), `count` (межа довжини чи кількості елементів), `limit` (межа `minimum` чи `maximum`) або `type` (єдиний тип, який мало мати значення) і порожній, якщо нічого з цього не застосовується, як для `enum` чи `pattern` або для `type`, що допускає кілька типів. Записи ніколи не містять регулярного виразу, допустимих значень чи значення, яке не пройшло перевірку; `message`, як і раніше, описує одну невдачу англійською.

Помилок валідації запиту (`validation_error`) у таблиці немає: в усіх API `details` у них має вигляд `{"errors": [...]}` — це список записів валідації, кожен із `loc`, `type` і `msg`, тобто формат, відмінний від формату `invalid_payload`. Див. розділ [Валідація запиту](#codes-validation).

### Ідентифікатор запиту {#request-id}

`error.request_id` має те саме значення, що й заголовок `X-Request-ID` у кожній відповіді, яку надсилає API, тож запит ідентифікує будь-який із них. Якщо ваш запит надсилає заголовок `X-Request-ID` (до 128 символів: літер, цифр, `.`, `_` або `-`), API використовує це значення як ідентифікатор запиту; інакше створює власний. Якщо ви його задаєте, робіть його унікальним для кожного запиту, щоб ідентифікатор указував на один виклик. Деякі відповіді надходять не від API, а від edge-рівня перед API: напр. `502` чи `504` або `413` для тіла, надто великого, щоб дійти до API. Вони не містять ні тіла помилки API, ні `X-Request-ID`. Спершу читайте тіло, а якщо його немає, беріть заголовок, як це робить [патерн обробки](#pattern), і будьте готові, що в таких відповідях не буде ні того, ні іншого. Що робити з ідентифікатором, описано в розділі [Повідомлення про баги](#bugs).

## Сімейства кодів статусу {#families}

| Сімейство статусів | Що означає сімейство |
|---|---|
| `200`/`201`/`202`/`204` | Успіх |
| `400` | Запит не вдалося прочитати в тому вигляді, у якому його надіслано |
| `401` | Немає придатних облікових даних: їх не надіслано або відкликано. Inboxes і Request Bins також відповідають `401`, як `invalid_credential`, на ключ, якого не розпізнають або не можуть перевірити, а Webhooks відповідає `401`, як `unauthorized`, на вхідну подію, підпис якої не проходить перевірку |
| `402` | Запит блокує ваш план або стан білінгу: квота, функція, якої немає у вашому плані, або заморожений чи призупинений робочий простір |
| `403` | Не дозволено. Webhooks також відповідає `403`, як `invalid_credential`, на облікові дані, яких не розпізнає |
| `404` | Ресурсу не існує *або* той, хто викликає, не може його бачити (ці випадки навмисно не розрізняються) |
| `405` | Шлях існує, але не для цього методу |
| `409` | Конфлікт із наявним станом, зокрема `Idempotency-Key`, повторно використаний з іншим тілом |
| `413` | Тіло завелике |
| `422` | Запит розібрано, але він не пройшов валідацію |
| `429` | Перевищено ліміт запитів |
| `5xx` | Проблема на боці сервера |

`429` і `5xx` — єдині сімейства, у яких повторне надсилання того самого запиту може вдатися. Для будь-якого іншого `4xx` код підказує, що змінити.

## Коди помилок {#codes}

Два API мають здебільшого спільні коди й після оновлення, згаданого на початку цієї сторінки, майже кожну спільну ситуацію позначають однаково. Відрізняються дві: `invalid_credential` — це `401` в Inboxes і `403` у Webhooks, а сесія входу, що спливла, — це `unauthorized` (`details.reason` `invalid`) в Inboxes, але `invalid_credential` у Webhooks. Стовпець **API** вказує, який API надсилає кожен код.

Request Bins надсилає ті самі коди, що й Inboxes, для тих самих ситуацій, зокрема й для цих двох. У стовпці **API** значення **Усі** означає всі три API, **Обидва** — Webhooks і Inboxes, а рядок із позначкою **Request Bins** стосується лише цього API.

### Автентифікація та авторизація {#codes-auth}

| `code` | Статус | API | Що це |
|---|---|---|---|
| `unauthorized` | 401 | Усі | Облікові дані не надіслано або їх відкликано. В Inboxes і Request Bins — також сесія входу, яка завершилася або не пройшла перевірку; кожен `unauthorized`, який вони надсилають, містить `details.reason`. У Webhooks — також вхідна подія на `POST /v1/ingest/{source_id}`, підпис якої не проходить перевірку (`details.reason` `invalid`); кожен `401` від Webhooks містить `details.reason` ([Що містить `details`](#details)). |
| `invalid_credential` | 401 в Inboxes і Request Bins, 403 у Webhooks | Усі | API-ключ або токен, якого API не розпізнає або не може перевірити. Замініть його: повторне надсилання тих самих облікових даних не допоможе. У Webhooks сюди належить і сесія входу, що спливла: увійдіть знову. |
| `forbidden` | 403 | Усі | Облікові дані дійсні, але цього не дозволяють: бракує області дії чи ролі, ключ, обмежений певними проєктами, використано поза ними або продукт не ввімкнено для вашого робочого простору. `details.reason` указує, що саме. |

`invalid_credential` — це `403` в API Webhooks і `401` в Inboxes і Request Bins, і так і залишиться: розгалужуйте обробку за кодом, а не за статусом. Формат запиту описано на сторінці [Автентифікація](/docs/authentication).

### Валідація запиту {#codes-validation}

| `code` | Статус | API | Що це |
|---|---|---|---|
| `validation_error` | 422 | Усі | Тіло, query чи шлях не пройшли валідацію або, у Webhooks, правило, яке API перевіряє сам, відхилило поле. `details` має вигляд `{"errors": [...]}` — це список записів. |
| `bad_request` | 400 | Усі | Запит не можна виконати в тому вигляді, у якому його надіслано. `message` пояснює чому. В Inboxes і Request Bins — тіло, яке API не зміг прочитати, напр. таке, що не є дійсним UTF-8. |
| `payload_too_large` | 413 | Усі | Тіло перевищує ліміт розміру. |
| `method_not_allowed` | 405 | Усі | Шлях існує, але не для цього методу. |

Кожен запис валідації описує одне вхідне значення, що не пройшло перевірку: `loc` указує де (`["body", "event_type"]`), `type` — що не так, у машинозчитуваному вигляді (`missing`, `string_too_long`, `json_invalid`, …), а `msg` пояснює це англійською. Якщо правило має число, запис також містить його в `params`: `count` для довжини (`string_too_short`, `string_too_long`, `too_short`, `too_long`) і `limit` для межі (`greater_than`, `greater_than_equal`, `less_than`, `less_than_equal`). Тіло, яке не є дійсним JSON, — теж помилка валідації, з типом `json_invalid`; в Inboxes і Request Bins тіло, яке не є дійсним UTF-8, натомість дає `400` `bad_request`.

Webhooks також надсилає власні типи записів — для правил, які перевіряє сам:

- `webhooks.max_attempts_above_plan`: `max_attempts` понад стелю плану, у `POST /v1/endpoints` або `PATCH /v1/endpoints/{id}`; `loc` `["body", "max_attempts"]`, з `params.count` — стелею.
- `webhooks.url_not_https`: `url` ендпоінта не https, у `POST /v1/endpoints`, `PATCH /v1/endpoints/{id}` або `POST /v1/operational-endpoints`; `loc` `["body", "url"]`.
- `webhooks.end_before_start`: масовий реплей, у якого `to` раніше за `from`; `loc` `["body", "to"]`. Однакові межі допускаються.
- `webhooks.end_not_after_start`: на маршруті для операторів платформи — вікно споживання, яке не закінчується пізніше, ніж починається; `loc` `["query", "end"]`.
- `webhooks.unknown_delivery_status`: невідомий фільтр `status` у `GET /v1/deliveries`; `loc` `["query", "status"]`, з `params.status` — надісланим значенням.
- `webhooks.unknown_operational_event_type`: значення `event_types`, яке не є операційним типом події, у `POST /v1/operational-endpoints`; `loc` `["body", "event_types", <index>]`, по одному запису на кожне окреме значення, за його першим індексом, з `params.event_type` — цим значенням — і `params.choices` — операційними типами подій, які приймає API.

На тому самому маршруті для операторів платформи дата вікна споживання, яку не вдається розібрати, дає запис `date_parsing` на `["query", "start"]` або `["query", "end"]`, по одному на кожну таку дату. Відмова за правилом, яке API перевіряє сам, містить щонайбільше 20 записів.

Правила, які Webhooks перевіряє сам, — щодо користувацьких заголовків, затримок `retry_schedule` і полів брокера джерела RabbitMQ — надсилають записи з власним `type`, з тими `loc` і `msg`, які вони мали завжди (крім назви заголовка, описаної в примітці від 2026-10-16), і з `params`, що містять значення, які називає правило:

- Понад 20 користувацьких заголовків: `too_long`, з `params.count`, `20`.
- Назва користувацького заголовка, яка не є дійсним HTTP-токеном: `webhooks.custom_header_name_invalid`, без `params`.
- Розрив рядка чи інший керувальний символ у значенні користувацького заголовка: `webhooks.custom_header_control_character`, з `params.header` — назвою заголовка.
- Значення користувацького заголовка понад 1024 символи: `webhooks.custom_header_value_too_long`, з `params.header` і `params.count`, `1024`.
- Назва, яку API резервує для власних заголовків доставки (`Content-Type`, `User-Agent` або будь-яка назва, що починається з `X-Webhook-`): `webhooks.custom_header_managed`, з `params.header`.
- Назва hop-by-hop-заголовка чи заголовка керування зʼєднанням, як-от `Host` або `Connection`: `webhooks.custom_header_forbidden`, з `params.header`.
- Значення користувацького заголовка із символом поза ASCII: `webhooks.custom_header_not_ascii`, з `params.header`.
- Назви й значення користувацьких заголовків, які разом займають понад 8192 байти: `webhooks.custom_headers_too_large`, з `params.limit`, `8192`.
- Затримка в `retry_schedule`, менша за 0 або більша за 604800 секунд: `webhooks.retry_delay_out_of_range`, з `params.limit`, `604800`.
- Джерело RabbitMQ, створене не з усіма полями брокера: `webhooks.broker_fields_required`, з `params.missing` — списком полів (з-поміж `broker_identifier`, `broker_host`, `broker_user`, `broker_exchange` і `broker_topic`), які були відсутні чи порожні. Його `loc` — `["body"]`.

`loc` правил щодо користувацьких заголовків — `["body", "custom_headers"]`, а `params.header` — назва в тому вигляді, у якому ви її надіслали; значення заголовка ніколи не повертається. Назва плану, якої API не знає, на маршруті для операторів платформи дає запис `enum` без `params`. До оновлення, згаданого на початку цієї сторінки, усі ці записи мали тип `value_error`.

Inboxes надсилає один власний тип запису: `inboxes.search_conflict` — для пошуку повідомлень у `GET /v1/inboxes/{id}/messages` або `GET /v1/messages`, який задає `header` з `in`, встановленим у `subject`, `from` або `body`. Його `loc` — `["query", "in"]`, і `params` він не містить ([Пошук повідомлень](/docs/product-inboxes#search)).

Request Bins надсилає три:

- `bins.nul_character`: символ NUL у шляху, рядку query чи тілі JSON, якого він не може зберегти. Його `loc` — `["path"]`, `["query", <name>]` або `["body"]`, і `params` він не містить.
- `bins.forward_target`: URL пересилання, на який bin не пересилатиме. Його `loc` — `["body", "forward_url"]`, а `params.reason` пояснює чому ([Пересилання](/docs/product-bins/reference#forwarding)).
- `bins.search_conflict`: пошук у `GET /v1/bins/{id}/requests` або `GET /v1/requests`, у якому `header` чи `field` не поєднується з його `in` (тоді `loc` — `["query", "in"]`) або який задає водночас `header` і `field` (тоді `loc` — `["query", "field"]`). Цей запис не містить `params` ([Перехоплені запити](/docs/product-bins/reference#requests)).

Мітка Inboxes, що на один символ перевищує свій ліміт:

```json
{
  "error": {
    "code": "validation_error",
    "message": "request validation failed",
    "details": {
      "errors": [
        {
          "loc": ["body", "label"],
          "msg": "String should have at most 200 characters",
          "type": "string_too_long",
          "params": {"count": 200}
        }
      ]
    },
    "request_id": "a3e81f0c5b9d4e2f8c7a6b5d4e3f2a1b"
  }
}
```

У Webhooks такий самий запис міститься в такому самому списку `details.errors` під тим самим кодом, а Request Bins надсилає його для `label` bin-а, що перевищує 200 символів.

### Коди API Webhooks {#codes-webhooks}

Ці коди належать до власних обʼєктів API Webhooks (типи подій, схеми, джерела, ендпоінти, доставки), і всі вони — `422`:

| `code` | Що це |
|---|---|
| `unknown_event_type` | Типу події немає в каталозі вашого робочого простору, а каталог приймає лише зареєстровані типи. |
| `invalid_payload` | Payload не відповідає схемі, зареєстрованій для його типу події (`details.reason` `payload`, з `details.errors`), або схема, яку ви реєструєте, не є дійсною JSON Schema (`schema_invalid`). |
| `schema_too_large` | JSON Schema, яку ви зареєстрували, завелика або має надто глибоку вкладеність. |
| `schema_pattern_unsafe` | `pattern` у вашій схемі задовгий, не компілюється або може виконуватися надто довго. |
| `schema_ref_unsupported` | Ваша схема використовує `$ref`, який API не розвʼязує. |
| `provider_secret_required` | Для ротації джерела Stripe чи GitHub потрібен новий секрет від цього провайдера, а для ротації джерела RabbitMQ — новий пароль брокера. `details.provider` указує, який саме: `stripe`, `github` або `rabbitmq`. |
| `broker_not_allowed` | Джерело RabbitMQ називає брокер, до якого API не підключатиметься. |

### План і білінг {#codes-plan}

Усі ці коди — `402`. Повтор того самого запиту ніколи не допомагає: хтось має змінити план, погасити платіж, дочекатися наступного розрахункового періоду або вивільнити місце в межах ліміту, напр. звільнивши адресу чи видаливши ендпоінт.

| `code` | API | Що це |
|---|---|---|
| `quota_exceeded` | Обидва | Перевищено ліміт плану: виділений обсяг (Inboxes: адреси; Webhooks: ендпоінти) або місячну стелю (Inboxes: повідомлення; Webhooks: доставки), коли треба дочекатися наступного періоду або перейти на вищий план. В обох API `details.reason` указує, що саме, а `details` називає `metric`, його `limit` і, для виділеного обсягу, поточну кількість `current`. |
| `quota_exceeded` | Request Bins | Перевищено ліміт плану на bin-и під час створення bin-а. `details.reason` дорівнює `allocation`, а `details` називає `metric` (`bins`), його `limit` і поточну кількість `current`. Місячний ліміт запитів ніколи не відхиляє виклик API: коли його вичерпано, bin-и відповідають відправникам і нічого не записують, доки за рахунок [кредиту](/docs/product-bins/reference#credit) не буде докуплено запитів або не почнеться наступний місяць. |
| `not_entitled` | Усі | Функції немає у вашому плані, як-от API читання на безкоштовному плані Inboxes, читання перехоплених запитів з API-ключем на плані Free у Request Bins або джерело RabbitMQ на плані, нижчому за Pro, у Webhooks. `details.feature` називає цю функцію. |
| `workspace_frozen` | Усі | Є непогашений платіж, тому зміни відхиляються. Погасіть його в консолі акаунта; доти перехід на вищий план теж відхилятиметься. |
| `workspace_suspended` | Усі | Пільговий період після непогашеного платежу закінчився, і сервіс для цього робочого простору зупинено. |

`quota_exceeded` — це `402`, а не `429`. Ліміт запитів знімається сам за кілька секунд; квота — ні.

У Webhooks ліміт ендпоінтів — це `quota_exceeded` у `POST /v1/endpoints` з `details.reason` `allocation`, `metric` `endpoints`, `limit` (стеля плану) і `current` (кількість ендпоінтів робочого простору). Джерело RabbitMQ на плані, нижчому за Pro, — це `not_entitled` з `details.feature` `rabbitmq_sources`: у `POST /v1/sources`, а також у `PATCH /v1/sources/{id}` для джерела RabbitMQ, тіло якого встановлює `status` у `enabled` або задає будь-яке з полів `broker_identifier`, `broker_host`, `broker_port`, `broker_vhost`, `broker_user`, `broker_exchange`, `broker_topic` чи `broker_queues`, навіть якщо значення не змінюється. Інші зміни, як-от перейменування чи вимкнення джерела, залишаються дозволеними. `max_attempts` понад стелю плану — це не `402`, а `422` `validation_error` ([Валідація запиту](#codes-validation)).

У Request Bins ліміт bin-ів — це `quota_exceeded` у `POST /v1/bins`. Читання перехоплених запитів з API-ключем на Free — це `not_entitled` з `details.feature` `read_api` у `GET /v1/bins/{id}/requests`, `GET /v1/requests`, `GET /v1/bins/{id}/paths` і `GET /v1/requests/{id}`; консоль читає їх на будь-якому плані. Задання URL пересилання чи надсилання тесту на Free — теж `not_entitled`, з `details.feature` `forwarding`. Поки робочий простір заморожений чи призупинений, кожен запит на запис, крім видалення, відхиляється з `workspace_frozen` або `workspace_suspended`, а читання лишається доступним. Bin-и продовжують записувати, поки робочий простір заморожений, і зупиняються, поки він призупинений ([Плани й ліміти](/docs/product-bins/reference#limits)).

| `code` | Статус | API | Що це |
|---|---|---|---|
| `not_found` | 404 | Усі | Ресурсу не існує, або ви не можете його бачити. Ці два випадки навмисно не розрізняються. `details.reason` називає тип ресурсу, а `details.id` — ідентифікатор, який ви запитали, якщо він є; відповідь для шляху, якого не існує, не містить `details` ([Що містить `details`](#details)). |

### Конфлікти {#codes-state}

| `code` | Статус | API | Що це |
|---|---|---|---|
| `conflict` | 409 | Webhooks | Запит конфліктує з наявним станом: назва вже зайнята або `Idempotency-Key` повторно використано з іншим тілом ([Ідемпотентність](/docs/idempotency#conflicts)). `details.reason` указує, що саме, — одне зі значень з таблиці нижче. |

Кожне значення `details.reason`, яке може містити `conflict`, коли його надсилають, та інші ключі в `details`:

| `details.reason` | Коли | Інші ключі в `details` |
|---|---|---|
| `event_type_exists` | Тип події з такою назвою вже зареєстровано в тих самих межах: в усьому робочому просторі або в проєкті, який ви вказали. | `event_type`: назва |
| `project_not_empty` | Видалення проєкту, у якому ще є ендпоінти чи джерела. Спершу видаліть їх. | `id`: проєкт. `endpoints` і `sources`: скільки їх у ньому |
| `idempotency_key_reuse` | `Idempotency-Key` повторно використано з іншим тілом ([Ідемпотентність](/docs/idempotency#webhooks)). Оригінальна подія лишається в силі. | `idempotency_key`: ключ |
| `delivery_not_redeliverable` | Спроба повторно доставити доставку, яка ще стоїть у черзі або надсилається. Повторно доставити можна лише доставку в стані `sent`, `failed` або `dead`. | `id`: доставка. `state`: `queued`, `sending`, `sent`, `failed` або `dead`, або `missing`, якщо доставку тим часом видалили |
| `delivery_exists` | Реплей події на ендпоінт, який уже має доставку цієї події. Натомість повторно доставте цю доставку. | `event_id` і `endpoint_id` |
| `endpoint_not_enabled` | Реплей події на ендпоінт, який вимкнено — вами або автоматично після повторних збоїв. | `id`: ендпоінт. `state`: `disabled` (вами) або `auto_disabled` (автоматично) |
| `endpoint_suspended` | Реплей події на ендпоінт, який ми призупинили. | `id`: ендпоінт. `cause`: `abuse`, `non_payment` або `plan_downgrade`; якщо причин кілька — найсерйозніша, а якщо жодна не застосовується, поле відсутнє |
| `endpoint_has_pending_deliveries` | Видалення ендпоінта, у якого ще є доставки в черзі, у процесі надсилання або в очікуванні повтору. Ендпоінт вимикається, хоча видалення відхилено, тож нові доставки до нього не надходять; повторіть видалення, коли вони завершаться. | `id`: ендпоінт. `count`: кількість його незавершених доставок |
| `replay_across_projects` | Реплей події на ендпоінт в іншому проєкті. | `event_id` і `endpoint_id` |

Масовий реплей, у якого `from` пізніше за `to`, — не конфлікт, а `422` `validation_error` ([Валідація запиту](#codes-validation)).

### Ліміти запитів {#codes-rate}

| `code` | Статус | API | Що це |
|---|---|---|---|
| `rate_limited` | 429 | Обидва | Забагато запитів. Якщо `Retry-After` задано, зачекайте стільки секунд і повторіть запит; інакше збільшуйте паузу між спробами. `details.retry_after` містить те саме число в обох API, а в Inboxes ліміт окремої скриньки також встановлює `details.reason` у `inbox_rate`, з `details.rate_per_min`. |
| `rate_limited` | 429 | Request Bins | Понад 10 тестових надсилань на URL пересилання одного bin-а за хвилину. `details.retry_after` показує, через скільки секунд буде дозволено наступне. |

API Request Bins надсилає `rate_limited` лише для тестових надсилань ([Протестуйте URL пересилання](/docs/product-bins/reference#forward-test)). Його URL bin-ів обмежують, як швидко можуть надсилати відправники, і відповідають відправникові, що перевищив ліміт, кодом `429` з `Retry-After`, а не в цьому форматі JSON ([Що відповідає URL bin-а](/docs/product-bins/reference#edge-answers)).

### Сервер {#codes-server}

| `code` | Статус | API | Що це |
|---|---|---|---|
| `internal_error` | 500 | Усі | Щось зламалося на нашому боці. Ідемпотентні запити можна безпечно повторити. |
| `unavailable` | 503 | Inboxes | Тимчасово неможливо обслужити запит: приймання повідомлень вимкнено, а `details.reason` дорівнює `ingest_disabled`. Повторіть запит із backoff. |
| `unavailable` | 503 | Request Bins | Пересилання не може прийняти запит: задання URL пересилання чи надсилання тесту, коли пересилання вимкнено для всього сервісу (`details.reason` `forwarding_disabled`), або тест, який не було взято на надсилання протягом 3 секунд, тож нічого не надіслано (`forwarder_unavailable`). Повторіть запит пізніше. |

`502` чи `504` від edge-рівня перед API може надійти зовсім без тіла JSON. Вважайте `5xx`, який не вдається розібрати, придатним для повтору.

### Результати тестування й верифікації {#failure-reason}

Тестування чи верифікація ендпоінта Webhooks (`POST /v1/endpoints/{id}/test`, `POST /v1/endpoints/{id}/verify`) надсилає на нього запит і відповідає `200` з результатом — незалежно від того, вдався той запит чи ні, тож невдача тут не є відповіддю з помилкою. `delivered` під час тесту або `verified` під час верифікації показує, чи все спрацювало. У разі невдачі `error` описує її англійською, а `failure_reason` називає стабільним машинним рядком:

| `failure_reason` | Що сталося |
|---|---|
| `http_status` | Ендпоінт відповів статусом поза `2xx`; `status_code` указує яким. |
| `timeout` | Немає відповіді протягом тайм-ауту ендпоінта. |
| `tls_failed` | Не вдалося TLS-рукостискання, найчастіше тому, що сертифікат не проходить перевірку. |
| `dns_failed` | Не вдається розвʼязати імʼя хоста. |
| `connection_failed` | Будь-який інший збій зʼєднання, як-от відмова в зʼєднанні, його скидання чи недосяжність. |
| `blocked_address` | Імʼя хоста розвʼязується в приватну чи іншу непублічну адресу, на яку Webhooks ніколи не надсилає. |
| `challenge_not_echoed` | Лише для верифікації: ендпоінт відповів `2xx` без challenge-токена в тілі. |
| `url_changed` | Лише для верифікації: URL ендпоінта змінився, поки тривав challenge. Верифікуйте ще раз. |

`failure_reason` дорівнює `null` у разі успіху, а також у разі невдачі, якої не описує жодне з цих значень, — тоді єдиним описом є `error`. Як і `code`, це відкритий рядок, а не enum: передбачте варіант за замовчуванням для невідомого значення й розгалужуйте обробку за `failure_reason`, а не розбирайте `error`.

## Коли код перейменовують {#renames}

Inboxes і Webhooks завершили свої перейменування 2026-10-15, до запуску v1, а не через 12 місяців. В Inboxes `invalid_request` тепер `validation_error`, API-ключ або токен, якого API не розпізнає чи не може перевірити, — `invalid_credential` (як і раніше `401`), а статус без власного коду отримує код цього статусу, як-от `bad_request` для `400`. У Webhooks `internal` тепер `internal_error`, `unprocessable` тепер `validation_error`, а `plan_violation` більше немає: кожна його відмова надсилає код, який називав її `next_code`, зі статусом цього коду. Жоден з двох API зараз не надсилає `next_code`. Після запуску v1 про перейменування оголошуватимуть у [журналі змін](/changelog), а старе написання й далі надсилатиметься в `error.code` щонайменше 12 місяців після цього — той самий строк, який [політика застарівання](/docs/versioning#deprecation) дає полю.

Поки перейменування триває, помилка також містить `next_code`: написання, яке матиме `code`, коли перейменування завершиться. Саме це поле, а не заголовок відповіді `Deprecation`, повідомляє, що код помилки перейменовують.

Розгалужуйте обробку за `next_code`, якщо він є, і за `code` в іншому разі (`error.next_code ?? error.code`). Обробник, написаний так, не потребує змін, коли перейменування завершується: відтоді `code` має нове написання, а `next_code` для нього більше не надсилається. Якщо ви можете читати лише `code`, напр. через SDK, який передає тільки `code`, зіставляйте обидва написання, доки перейменування не завершиться.

Перейменування, що завершилися 2026-10-15, і відмови, які змінилися разом із ними:

| API | Ситуація | Раніше | Тепер |
|---|---|---|---|
| Inboxes | Запит, що не проходить валідацію | `422` `invalid_request`, `next_code` `validation_error` | `422` `validation_error` |
| Inboxes | API-ключ або токен, якого API не розпізнає або який не проходить перевірку | `401` `unauthorized`, `next_code` `invalid_credential` | `401` `invalid_credential` |
| Inboxes | Статус без власного коду, як-от для тіла, що не є дійсним UTF-8 | `error`, `next_code` — код, який цей статус має деінде | код цього статусу, як-от `400` `bad_request` |
| Inboxes | Облікові дані, обмежені певними проєктами | `403` `forbidden`, `details.reason` `project` | `403` `forbidden`, `details.reason` `project_confined` |
| Inboxes | `quota_exceeded`, `not_entitled` API читання й `rate_limited` для окремої скриньки | `details` також містило `max_inboxes`, `max_http_bins`, `monthly_messages`, `plan` або `inbox_id` | `details` містить лише ключі, перелічені в розділі [Що містить `details`](#details) |
| Webhooks | Кожен `500` | `internal`, `next_code` `internal_error` | `internal_error` |
| Webhooks | Поле, яке API перевіряє сам (`url` ендпоінта не https, невідомий фільтр `status` чи операційний тип події, вікно споживання, яке не вдається розібрати або яке не закінчується пізніше, ніж починається) | `422` `unprocessable`, `next_code` `validation_error` | `422` `validation_error` |
| Webhooks | Ліміт ендпоінтів (`POST /v1/endpoints`) | `402` `plan_violation`, `next_code` `quota_exceeded` | `402` `quota_exceeded`, `details.reason` `allocation` |
| Webhooks | `max_attempts` понад стелю плану (`POST /v1/endpoints`, `PATCH /v1/endpoints/{id}`) | `402` `plan_violation`, `next_code` `validation_error` | `422` `validation_error`, тип запису `webhooks.max_attempts_above_plan` |
| Webhooks | Джерело RabbitMQ на плані, нижчому за Pro | `402` `plan_violation`, `next_code` `not_entitled` | `402` `not_entitled`, `details.feature` `rabbitmq_sources` |
| Webhooks | Вимкнення верифікації ендпоінтів на плані, який її вимагає (`PATCH /v1/workspace`); зараз такого плану немає | `402` `plan_violation`, `next_code` `not_entitled` | `402` `not_entitled`, `details.feature` `optional_endpoint_verification` |
| Webhooks | Масовий реплей, у якого `from` пізніше за `to` (`POST /v1/deliveries/replay`) | `409` `conflict`, `details.reason` `replay_window_inverted` | `422` `validation_error`, тип запису `webhooks.end_before_start` на `["body", "to"]` |
| Webhooks | Правила, які Webhooks перевіряє сам, — щодо користувацьких заголовків, `retry_schedule`, полів брокера й назв планів | тип запису `value_error` | власний тип запису правила ([Валідація запиту](#codes-validation)); `loc`, `msg` і `params` без змін |
| Webhooks | Будь-яка помилка валідації | `details`: список записів | `details`: `{"errors": [...]}`, як в Inboxes |

Обробник, що розгалужував обробку за `error.next_code ?? error.code`, отримує той самий код, що й раніше, в усіх наведених вище ситуаціях, крім масового реплею. Обробник, який читав `error.details` як список у помилці валідації Webhooks, тепер читає `error.details.errors`; той, що читав вилучені ключі `quota_exceeded` в Inboxes, читає `metric`, `limit`, `current` і `period`; той, що зіставляв причину `project` для `forbidden` в Inboxes, зіставляє `project_confined`; а той, що зіставляв `type` запису `value_error` у Webhooks, зіставляє власний тип правила.

`unauthorized` не виведено з ужитку: він лишається кодом для відсутніх чи відкликаних облікових даних в обох API, для сесії входу, що завершилася, в Inboxes і для вхідної події, підпис якої не проходить перевірку, у Webhooks.

## Коди, які раніше наводила ця сторінка {#earlier-versions}

Попередні версії цієї сторінки наводили коди й поля, указані ліворуч. API їх не надсилали; вони надсилають те, що праворуч. Два з них відтоді стали правдою — `request_id` у тілах помилок і `internal_error` в усіх API, — і їхні рядки пояснюють як.

| Попередні версії наводили | API надсилають |
|---|---|
| `validation_failed` (400) | `validation_error` (422) |
| `fields` | `details`: `{"errors": [...]}` в обох API |
| `request_id` у кожному тілі | Не надсилався, поки ті версії були актуальні: ідентифікатор був лише в заголовку відповіді `X-Request-ID`. Після оновлень, згаданих на початку цієї сторінки, кожне тіло помилки, яке надсилають API, теж його містить — як `error.request_id`, з тим самим значенням, що й заголовок ([Ідентифікатор запиту](#request-id)). |
| `malformed_json` (400), `unsupported_content_type` (415) | `validation_error` (422) |
| `request_too_large` | `payload_too_large` (413) |
| `no_credentials` (401) | `unauthorized` (401) |
| `invalid_credentials`, `expired_credentials` (401) | `invalid_credential`: `403` у Webhooks, `401` в Inboxes. Сесія входу, що спливла, — це `unauthorized` (401) в Inboxes |
| `scope_required`, `wrong_project` (403) | `forbidden` (403); `details.reason` пояснює чому (`scope`, `project`, `project_confined`, …), а `details.required` називає відсутню область дії |
| `already_exists`, `state_conflict`, `not_empty`, `idempotency_key_reused` (409) | `conflict` (409); `details.reason` указує, що саме (`event_type_exists`, `project_not_empty`, `idempotency_key_reuse`, …) |
| `rate_limit_exceeded` | `rate_limited` (429) |
| `quota_exceeded` як 429 | `quota_exceeded` як 402 |
| `internal_error` в усіх API | `internal_error` в обох API з 2026-10-15; раніше Webhooks надсилав `internal` |
| `service_unavailable` (503), `gateway_timeout` (504) | `unavailable` (503) в Inboxes, коли приймання повідомлень вимкнено, і в Request Bins, коли пересилання не може прийняти запит; `502`/`504` від шлюзу може не мати тіла JSON |

## Патерн обробки {#pattern}

```ts
async function call(): Promise<Event> {
  const res = await fetch(url, opts)
  if (res.ok) return await res.json()

  // A gateway 502/504 can arrive without a JSON body
  const body = await res.json().catch(() => null)
  const error = body?.error ?? { code: 'error', message: res.statusText }
  // Log this with every error; the header carries it when the body doesn't
  const requestId = error.request_id ?? res.headers.get('X-Request-ID')
  // While a code is being renamed, next_code is what it will become: prefer it
  const code = error.next_code ?? error.code

  // Switch on the code, not the status: one status can carry several codes
  switch (code) {
    case 'rate_limited': {
      const wait = Number(res.headers.get('Retry-After') ?? '1')
      await sleep(wait * 1000)
      return call() // retry
    }
    case 'invalid_credential': // All: a key the API can't accept (403 on Webhooks, 401 on Inboxes and Request Bins)
    case 'unauthorized': // All: no usable credential
      // The credential is missing or bad: replace it rather than retry with it
      throw new CredentialError(error, requestId)
    case 'forbidden': {
      // Optional refinement: why it was refused, and what would have been allowed
      const reason = error.details?.reason // 'scope', 'role', 'project', 'project_confined', 'csrf', …
      const required = error.details?.required // 'admin', 'member', 'read' or 'publish', when sent
      throw new PermissionError(error, requestId, reason, required)
    }
    case 'validation_error': { // All
      const entries = error.details?.errors ?? []
      throw new ValidationError(entries, requestId)
    }
    case 'quota_exceeded':
    case 'not_entitled':
      // Retrying won't help; the plan has to change, or the period has to roll over
      throw new PlanError(error, requestId)
    default:
      // Unknown code, but the family tells us the rough shape
      if (res.status >= 500) {
        // Server-side; safe to retry idempotent ops
        throw new RetryableError(error, requestId)
      }
      throw new TerminalError(error, requestId)
  }
}
```

Загальне правило: **розгалужуйте обробку за `error.next_code ?? error.code`, а за замовчуванням обробляйте за сімейством статусу**. Нові коди, додані до наявних статусів, нічого вам не зламають: їх обробить гілка за замовчуванням. `details.reason` уточнює випадок і ніколи його не замінює: причина, якої ви не розпізнаєте, обробляється так, як її код. Не розбирайте `message`; якщо значення призначене для коду, як-от ідентифікатор, якого не знайдено, чи досягнутий ліміт, воно є в `details`. Те саме правило діє для дашборда чи SDK, побудованих на цих API: опубліковані [SDK](/docs/product-webhooks/sdks) передають `error.code` без змін, тож розгалужуйте обробку за кодом, який містить виняток, і зіставляйте обидва написання коду, який перейменовують.

## Повідомлення про баги {#bugs}

Кожна відповідь, яку надсилає API, зокрема й відповідь із помилкою, містить заголовок `X-Request-ID`, і API дозволяють JavaScript у браузері його читати. Їхні тіла помилок містять той самий ідентифікатор як `error.request_id`. Коли щось не так на нашому боці (5xx, неочікувана поведінка), саме ідентифікатор запиту дає нам змогу знайти виклик у наших логах. Записуйте його в лог поруч із кожною помилкою й додавайте до звернень у підтримку.

Не публікуйте ідентифікатори запитів (вони не секретні, але будь-хто, у кого вони є, може розпитати нас про трафік вашого акаунта). Використовуйте їх у приватних каналах (підтримка, звернення з дашборда).
