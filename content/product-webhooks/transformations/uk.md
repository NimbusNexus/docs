# Трансформації

Трансформація змінює те, що отримує ендпоінт: вона запускається для кожної події, перш ніж ми її доставимо, і надсилає замість неї перетворений запит або взагалі нічого. Це або **конвеєр** декларативних кроків, доступний на кожному плані, або **скрипт** на JavaScript, доступний на платних планах; те, що вона створює, підписується секретом ендпоінта й надсилається, як будь-яка інша доставка.

## Для чого вона потрібна {#what-for}

- **Отримувач, якому потрібні облікові дані.** Ваш власний API або API партнера очікує bearer-токен, Basic-автентифікацію чи API-ключ. Конвеєр додає їх із [секрету](#credentials), який ми зберігаємо в зашифрованому вигляді й більше ніколи не показуємо.
- **Отримувач, якому потрібен власний формат.** Slack, Discord і Microsoft Teams приймають лише власні формати повідомлень і відхиляють наш конверт; CRM хоче три поля з власними назвами. Таке тіло будує [шаблон](#templates) або крок `map`.
- **Лише деякі події.** [Підписка](/docs/product-webhooks#objects) зіставляється лише за типом події. Для умови «лише `invoice.paid` на суму від $1 000» потрібен payload, а крок `filter` його читає.
- **Менше даних або трохи більше.** Приберіть персональні дані, перш ніж їх побачить сервіс аналітики, або додайте тип події в тіло чи в заголовок.

## Конвеєри та скрипти {#kinds}

| | Конвеєр | Скрипт |
|---|---|---|
| Що ви пишете | До 20 кроків — у формі в консолі або як JSON | Одну функцію на JavaScript |
| Плани | Кожен план, зокрема Free | Starter, Pro і Custom |
| Де виконується | Поруч із доставкою, у фіксованих межах; жоден ваш код не виконується | В окремій пісочниці, з бюджетом CPU, памʼяті й часу |
| Для чого | Облікові дані, фільтри, вилучення й додавання полів, зміна формату, повідомлення в чати | Логіка, яку не виразити кроками |

Трансформація — це або одне, або інше, і її вид фіксується під час створення. На ендпоінті може бути щонайбільше одна трансформація; одна трансформація може обслуговувати кілька ендпоінтів свого проєкту.

На Free створення або тестування скрипту відхиляється з `402 not_entitled`. Робочий простір, який відмовився від платного плану, зберігає свої скрипти: їх і далі можна перейменовувати, призупиняти, відʼєднувати й видаляти, але не можна зберігати новий код, тестувати чи відновлювати; доставки на ендпоінт, що виконує скрипт, чекають, доки план знову не включатиме скрипти або доки ви не відʼєднаєте скрипт. Конвеєри й далі працюють на будь-якому плані.

Скрипти залежать від окремого сервісу пісочниці, конвеєри — ні. Поки скрипти вимкнено, консоль про це повідомляє, `GET /v1/plan` повертає `transformations_available: false`, а доставки на ендпоінт, що виконує скрипт, чекають. Якщо пісочниця саме не може прийняти скрипт, збереження чи тестування скрипту відповідає `503 unavailable` і нічого не зберігає, а спроба доставки завершується невдачею з відповідним повідомленням і повторюється за звичайним розкладом.

`GET /v1/plan` також показує, що входить у ваш план: `pipelines` дорівнює `true` на кожному плані, а `transformations` — `true`, коли план включає скрипти. Запуски обох видів рахуються, але не тарифікуються; `transformation_runs` — їхня кількість за цей місяць.

## Конвеєр {#pipeline}

Конвеєр — це JSON-документ. Цей надсилає оплачені рахунки на суму від $1 000, без email клієнта й будь-яких номерів телефону, з типом події, доданим у тіло, і bearer-токеном зі збереженого секрету:

```json
{
  "version": 1,
  "steps": [
    { "filter": { "type": "invoice.paid", "data": { "amount": { "$gte": 100000 } } }, "note": "Paid invoices of $1,000 or more" },
    { "drop": ["data.customer.email", "**.phone"] },
    { "set": { "event_type": "{{ type }}" } },
    { "auth": { "type": "bearer", "secret": "sec_…" } }
  ]
}
```

`version` — це формат документа, завжди `1`, а не версія трансформації. Кроки виконуються в тому порядку, у якому записані. Кожен — це обʼєкт з одним ключем кроку й, за бажання, `note` до 200 символів: консоль показує її на кроці, а доставка, яку відкинув фільтр, її записує. `filter` також може мати `action`.

Перший крок бачить конверт, який ми інакше надіслали б, з його `id`, `type`, `created_at`, `data` і `version`, а кожен наступний крок бачить тіло таким, яким його залишив попередній. Якщо жоден крок не змінює тіло, отримувач отримує оригінальні байти події. В API й текстах помилок кроки нумеруються з 0, а в редакторі консолі — з 1.

| Крок | У консолі | Що робить |
|---|---|---|
| `filter` | **Filter** | Надсилає подію, лише якщо вона збігається, або, з `"action": "drop"`, відкидає її, якщо збігається. |
| `drop` | **Remove fields** | Вилучає поля з тіла. |
| `set` | **Set fields** | Додає або перезаписує поля. |
| `map` | **Reshape the body** | Замінює тіло тим, яке будуєте ви. |
| `headers` | **Headers** | Задає, вилучає або перейменовує заголовки. |
| `auth` | **Credential** | Додає bearer-токен, Basic-автентифікацію чи API-ключ зі збереженого секрету. |

### `filter` {#step-filter}

Залишає доставку, лише якщо подія збігається; інакше доставка [відкидається](#dropped), і нічого не надсилається. З `"action": "drop"` усе навпаки: відкидається те, що збігається.

```json
{ "filter": { "data": { "status": "paid", "amount": { "$gte": 100000 } } }, "note": "Paid, $1,000 or more" }
```

- Кожен ключ — це умова, і виконуватися мають усі. Вкладений обʼєкт перевіряється за формою, як тут `data`.
- Просте значення збігається за рівністю JSON: `1` дорівнює `1.0`.
- Масив збігається, коли він дорівнює значенню або коли збігається один з його елементів: `{"data": {"tags": "urgent"}}` виконується для `["billing", "urgent"]`, а `{"data": {"items": {"sku": "A-1", "qty": 2}}}` потребує одного елемента, у якому є обидва.
- Поле, якого в події немає, збігається лише з `{"$exists": false}` і запереченнями, як-от `$neq`.
- Оператори: `$eq`, `$neq`, `$gt`, `$gte`, `$lt`, `$lte` (числа з числами, текст із текстом; мітки часу ISO порівнюються за часом), `$in`, `$nin`, `$exists`, `$startsWith`, `$endsWith`, `$contains` (текст або масив, що містить значення), а також `$and`, `$or` і `$not`, щоб поєднувати фільтри.
- `$meta` перевіряє, куди йде доставка: `{"$meta": {"endpoint": {"id": "ep_3f9a…"}}}`.

### `drop` {#step-drop}

Вилучає поля з тіла: список від 1 до 50 шляхів. `*` відповідає будь-якому одному рівню, а `**` — будь-якій глибині, тож `**.email` вилучає кожне поле `email`, хоч би де воно було. Шлях, який нічому не відповідає, не є помилкою.

```json
{ "drop": ["data.customer.email", "data.cards[*].number", "**.phone"] }
```

### `set` {#step-set}

Додає або перезаписує поля: від 1 до 50 пар зі шляху й [значення](#values). Відсутні обʼєкти дорогою створюються, і кожне значення читає тіло таким, яким його застав крок. Шлях, що натрапляє на значення, яке не є обʼєктом, провалює запуск з `set_conflict`.

```json
{ "set": { "event_type": "{{ type }}", "data.total_cents": { "$ref": "data.amount" } } }
```

### `map` {#step-map}

Замінює тіло [значенням](#values), яке пишете ви, — зазвичай обʼєктом.

```json
{ "map": {
    "invoice_id": "{{ data.id }}",
    "amount": { "$ref": "data.amount" },
    "amount_display": "{{ data.amount | money(data.currency) }}",
    "event": "{{ type }}"
} }
```

Для події `invoice.paid`, у якої `data` — це `{"id": "in_42", "amount": 150000, "currency": "usd"}`, крок надсилає:

```json
{ "invoice_id": "in_42", "amount": 150000, "amount_display": "1,500.00 USD", "event": "invoice.paid" }
```

### `headers` {#step-headers}

Задає заголовки через `set`, вилучає їх через `remove` і перейменовує через `rename` — у порядку remove, rename, set. Назви збігаються незалежно від регістру. Конвеєр починає без власних заголовків: користувацькі заголовки ендпоінта й наші додаються після того, як він виконається, заголовок, який він задає, замінює користувацький заголовок з тією самою назвою, а `remove` і `rename` діють лише на заголовки, задані попередніми кроками.

```json
{ "headers": { "set": { "X-Event-Type": "{{ type }}", "Content-Type": "application/json" } } }
```

Конвеєр не може задати заголовок, який ми надсилаємо самі, — тобто жоден заголовок `X-Webhook-*`, зокрема підпис, і `User-Agent`, — а також заголовок, що належить зʼєднанню, як-от `Host`, `Content-Length` чи `Expect`. `Content-Type` задавати можна, і він стає типом вмісту доставки. Без нього доставка надсилається як `application/json`.

### `auth` {#step-auth}

Додає облікові дані зі [збереженого секрету](#credentials), указаного за ідентифікатором:

| `type` | Що додає |
|---|---|
| `bearer` | `Authorization: Bearer` і секрет. |
| `basic` | `Authorization: Basic` з `username` і секрету як пароля. |
| `api_key`, `"in": "header"` | Секрет у заголовку з назвою `name`, після необовʼязкового `prefix`, як-от `"Token "`. |
| `api_key`, `"in": "query"` | Секрет як параметр запиту `name` в URL ендпоінта, лише для цього запиту. |

```json
{ "auth": { "type": "api_key", "in": "header", "name": "X-Api-Key", "secret": "sec_…" } }
```

Кроки `auth` стоять після всіх інших кроків, тож жоден крок не може прочитати, скопіювати чи перевірити облікові дані.

## Шляхи та значення {#values}

Шлях указує на поле тіла:

| Шлях | Указує на |
|---|---|
| `data.customer.email` | Поле. |
| `data.items[0].sku` | Елемент списку. |
| `data['first name']` | Ключ, у якому є пробіл, крапка чи дужка. |
| `data.items[*].sku` | Кожен елемент; у значенні — їхній список. |
| `**.email` | `email` на будь-якій глибині; лише в `drop`. |
| `$meta.endpoint.id` | Ендпоінт, куди йде доставка, а `$meta.endpoint.description` — його опис; лише в значенні. |

`set` приймає прості шляхи, `drop` — `*` і `**`, а значення читає з `*`, але не з `**`.

Значення в `set`, `map` чи заголовку — це JSON, який копіюється так, як записаний, за двома винятками:

- **`{{ path }}`** у рядку вставляє значення як текст. Відсутнє значення чи `null` нічого не вставляє, а обʼєкт або список вставляється як JSON. `{{ 'text' }}` і `{{ 42 }}` — літерали, тож буквальне `{{` записується як `{{ '{{' }}`.
- **`{"$ref": "path"}`** вставляє саме значення й зберігає його тип: число лишається числом, список — списком. Додайте `"default"` на випадок, коли шляху немає.

Вираз може пропустити своє значення через фільтри, зліва направо: `{{ data.amount | money(data.currency) }}` дає `1,500.00 USD` для суми 150000 у `usd`.

| Фільтр | Дає |
|---|---|
| `upper`, `lower` | Текст великими чи малими літерами. |
| `default(x)` | `x`, коли значення немає, воно `null` або порожнє. |
| `truncate(n)` | Щонайбільше `n` символів, а далі `…`. |
| `join(sep)` | Список як текст, зʼєднаний через `", "`, якщо не вказати `sep`. |
| `length` | Кількість елементів, ключів чи символів. |
| `json`, `json(indent)` | Значення як компактний JSON або з відступом від 1 до 8 пробілів. |
| `number(digits)` | Число з такою кількістю знаків після коми. |
| `money(currency)` | Суму в мінімальних одиницях валюти, відформатовану; валюти без дробової частини й із трьома знаками теж. |
| `date(format)` | Час у форматі ISO 8601 або в секундах epoch, в UTC, з `%Y`, `%m`, `%d`, `%H`, `%M`, `%S` тощо. |
| `escape(target)` | Текст, який не може форматувати повідомлення в чаті: `slack` (за замовчуванням), `discord` або `markdown`. |
| `code(target, max, language)` | Текст як блок коду в розмітці `slack`, `discord` чи `markdown`, який текст не може завершити передчасно, обрізаний до `max` символів. |

Циклів, умов і обчислень немає: умова — це крок `filter`, а список стає текстом через `[*]` і `join`.

## Шаблони {#templates}

У галереї є готові конвеєри, з яких можна почати. У консолі вони під **Start from a template**, нижче кроків: **Use Slack message** або кнопка будь-якого іншого шаблону переносить його кроки в редактор — після запитання, якщо вони замінять ваші. Через API `GET /v1/transformations/templates` повертає кожен шаблон із його `pipeline`.

| Шаблон | Що надсилає |
|---|---|
| **Slack message** | Для вхідного вебхука Slack: тип події як заголовок повідомлення, її ідентифікатор і час, а дані — блоком коду. |
| **Discord message** | Для вебхука каналу Discord: embed із типом події, її даними блоком коду, ідентифікатором і часом. Нікого не згадує. |
| **Microsoft Teams card** | Для вебхука робочого процесу Teams: Adaptive Card із типом події, її ідентифікатором і часом, а дані — моноширинним шрифтом. |
| **Keep only these fields** | `id`, `type`, `created_at` і `version` події та лише ті поля `data`, які перелічує його `map`, починаючи з `data.id`. Перелічене поле, якого в події немає, надсилається як `null`. |
| **Drop personal data** | Подію без `email`, `phone`, `first_name`, `last_name`, `address`, `billing_address`, `shipping_address`, `date_of_birth` і `ip_address` на будь-якій глибині. Звичайне `name` лишається, бо воно часто називає план чи продукт. |

Після збереження шаблону ви отримуєте власний конвеєр: змінюйте його, як будь-який інший; із шаблоном він більше нічим не повʼязаний. Кожен шаблон для чату — це крок `map` і крок `headers`, що задає `Content-Type: application/json`, і працює він з будь-якою подією. Відсутній тип показується як «Event», а відсутній ідентифікатор чи час — як «—», дані обрізаються під обмеження застосунку, і ніщо в події не може відформатувати повідомлення, когось згадати чи передчасно завершити блок коду.

Slack, Discord і Teams не можуть відповісти на [challenge верифікації](/docs/product-webhooks/endpoint-verification#cannot-echo), тож ендпоінту, спрямованому на один із них, потрібна вимкнена верифікація в його проєкті — платні плани це дозволяють.

**Пресети тепер — шаблони.** Ендпоінт, який уже виконує пресет, тобто скрипт, і далі виконує його без змін, і лише такий ендпоінт досі пропонує **Preset** серед варіантів. Шаблон із тією самою назвою робить те саме без скрипту, на кожному плані.

## Облікові дані {#credentials}

Крок `auth` указує секрет за ідентифікатором (`sec_…`), а не за значенням. Секрет належить проєкту, як і трансформація, і вказати його можуть лише конвеєри цього проєкту. Його значення зберігається в зашифрованому вигляді й ніколи не повертається: API перелічує секрети за назвою та ідентифікатором, прочитаний конвеєр містить лише ідентифікатор, тест показує облікові дані як `••••`, а доставка зберігає лише назви заголовків і параметрів запиту, які вона додала.

У консолі поле **Secret** у кроці **Credential** перелічує секрети проєкту. Щоб зберегти новий, виберіть **New secret…**, заповніть **Secret name** і **Secret value** та натисніть **Save secret**.

Через API, зі значенням зі змінної середовища:

```bash
curl -sX POST {{WEBHOOKS_BASE_URL}}/v1/secrets \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"project_id\": \"prj_…\", \"name\": \"CRM token\", \"value\": \"$CRM_TOKEN\"}"
```

```json
{ "id": "sec_…", "project_id": "prj_…", "name": "CRM token", "transformation_count": 0, "created_at": "…", "updated_at": "…" }
```

`PATCH /v1/secrets/{id}` перейменовує секрет або замінює його значення; кожен конвеєр, що його вказує, надсилає нове значення з наступної спроби, зокрема в повторах попередніх доставок. `DELETE /v1/secrets/{id}` відхиляється з `409 secret_in_use`, поки поточна версія якогось конвеєра вказує цей секрет. Консоль лише створює секрети; перейменовуйте, замінюйте й видаляйте їх через API.

## Скрипти {#script}

Скрипт — це одна функція з назвою `transform`, на Starter, Pro і Custom:

```js
function transform(event, context) {
  // event:   { id, type, created_at, data, version }, the envelope we would otherwise send
  // context: { endpoint: { id, description }, attempt }
  if (event.type !== "invoice.paid") return null; // send nothing
  return {
    body: { text: `Invoice ${event.data.id} paid` },
    headers: { "X-Team": "billing" },
  };
}
```

Вона повертає запит, який треба надіслати, або `null`, щоб нічого не надсилати. `body`, що є обʼєктом чи списком, надсилається як JSON; рядок — як є, з `text/plain; charset=utf-8`. `contentType` задає інший тип вмісту замість заголовка `Content-Type`, а `headers` додає заголовки, для яких діють правила користувацьких заголовків ендпоінта. URL і метод беруться з ендпоінта. Усе, що скрипт виводить через `console.log`, зберігається разом із доставкою — до 4 KiB.

Скрипт — це звичайний JavaScript в одному файлі, без мережі, файлової системи, таймерів та імпортів, тож потрібну йому бібліотеку треба вбудувати в нього. Під час збереження ми спершу завантажуємо скрипт у пісочниці, не викликаючи його: синтаксична помилка, відсутня функція `transform` або код верхнього рівня, що падає, відхиляється з `422 invalid_transformation`, і нічого не зберігається.

## Тестування {#test}

**Test** під редактором запускає те, що в редакторі, — збережене чи ні — на **A recent event** з останніх доставок ендпоінта або на **An event you paste**. Натисніть **Run test**: нічого не надсилається й не зберігається. Конвеєр виконується із секретами свого проєкту, а результат показує всі облікові дані як `••••`. Результат — один із таких:

- **Would send**: тип вмісту, розмір, заголовки й тіло, які отримав би отримувач.
- **Would send nothing**: доставку відкинув фільтр на показаному кроці або скрипт повернув `null`.
- **Failed**: чому, а для конвеєра — ще й на якому кроці.

Через API надішліть конвеєр або `code` скрипту разом із подією:

```bash
curl -sX POST {{WEBHOOKS_BASE_URL}}/v1/transformations/test \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"project_id": "prj_…",
       "pipeline": {"version": 1, "steps": [
         {"map": {"text": "{{ type }}: {{ data.id }}"}},
         {"auth": {"type": "bearer", "secret": "sec_…"}}]},
       "event": {"id": "evt_1", "type": "invoice.paid", "created_at": "2026-11-03T10:00:00Z", "data": {"id": "in_42"}, "version": "1"}}'
```

```json
{ "status": "ok", "body": "{\"text\":\"invoice.paid: in_42\"}", "content_type": null, "headers": { "Authorization": "Bearer ••••" }, "logs": "", "reason": null, "error": null, "fuel": 0, "duration_ms": 0.2, "query": {}, "step": null }
```

`status` — це `ok`, `dropped` або `failed`. Коли доставку відкинуто чи запуск провалився, `step` — це крок, рахуючи з 0; `reason` — службове слово, як-от `no_match` (або `matched` для фільтра з `"action": "drop"`) чи `set_conflict`; а `error` пояснює це словами, з приміткою фільтра, якщо доставку відкинуто. `content_type` дорівнює `null`, якщо жоден крок його не задав. Навіть тест, який відкидає доставку чи провалюється, відповідає `200`, а от конвеєр, що ніколи не зміг би виконатися, відхиляється з `422 invalid_pipeline` — так само, як під час збереження.

Тестувати конвеєр можна на кожному плані. Тестування скрипту потребує плану зі скриптами, має спільний зі збереженням скриптів ліміт — 60 на хвилину на робочий простір, зі сплесками до 10, — і додатково повертає `logs` і `fuel` скрипту.

**Send test ping** ендпоінта надсилає фіксований пінг без трансформації, а отже й без облікових даних конвеєра: отримувач, який їх перевіряє, пінг відхилить. Що отримає ваш отримувач, покаже **Test** або справжня подія.

## Версії та призупинення {#versions}

Кожне збереження зміненого конвеєра чи скрипту створює наступну версію; збереження ідентичного поточній версії не створює жодної. Зберігаються останні 50 версій, і кожна доставка записує версію, яка її сформувала. У консолі **Versions** показує їх, а **Load into editor** завантажує попередню версію в редактор; після збереження вона стає найновішою. Через API `GET /v1/transformations/{id}/versions` перелічує їх від найновішої, а `GET /v1/transformations/{id}/versions/{version}` повертає одну разом із її конвеєром чи кодом.

**Pause** зупиняє трансформацію, не відʼєднуючи її, — так само, як `PATCH /v1/transformations/{id}` з `{"status": "disabled"}`. Доставки її ендпоінтів чекають, а не надсилаються без трансформації: вони показуються як `failed` з `last_error` «paused: the endpoint's transformation is not running» і надсилаються, коли ви відновите трансформацію через **Resume** (`{"status": "enabled"}`), — уже з тією версією, яка тоді буде поточною. Призупиняти й відновлювати конвеєр можна на будь-якому плані.

## Як підʼєднати до ендпоінта {#set-up}

У консолі відкрийте меню ендпоінта на сторінці **Endpoints** і виберіть **Transformation** або натисніть його запис у стовпці **Transformation**. Далі:

1. Оберіть **Pipeline** і зберіть конвеєр: через **Add a step**, із шаблону або вставивши цілий документ у **JSON** і натиснувши **Apply JSON**. Або оберіть **Script** і напишіть функцію.
2. [Протестуйте трансформацію](#test).
3. Натисніть **Save**. Наступні доставки ендпоінта проходитимуть через неї.

**Off** і **Save** вимикають її після підтвердження, і доставки знову надсилаються як конверт події. Якщо жоден інший ендпоінт її не виконує, трансформація видаляється разом із версіями. Оскільки вид змінити не можна, перемикання ендпоінта зі скрипту на конвеєр чи навпаки зберігає нову трансформацію замість старої й видаляє стару, якщо її не виконує жоден інший ендпоінт. Коли одна трансформація працює на кількох ендпоінтах, збереження змінює її для всіх.

Через API створіть трансформацію в проєкті ендпоінта, а потім підʼєднайте її до ендпоінта:

```bash
curl -sX POST {{WEBHOOKS_BASE_URL}}/v1/transformations \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "Paid invoices to the CRM", "project_id": "prj_…",
       "pipeline": {"version": 1, "steps": [
         {"filter": {"type": "invoice.paid"}, "note": "Paid invoices only"},
         {"drop": ["**.email"]},
         {"auth": {"type": "bearer", "secret": "sec_…"}}]}}'

curl -sX PATCH {{WEBHOOKS_BASE_URL}}/v1/endpoints/ep_3f9a… \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"transformation_id": "trf_…"}'
```

Скрипт передається в `code` замість `pipeline`; запит з обома полями або без жодного відхиляється. Щоб пізніше змінити документ, надішліть `PATCH /v1/transformations/{id}` з новим `pipeline`. `POST /v1/endpoints` теж приймає `transformation_id`, `{"transformation_id": null}` відʼєднує трансформацію, а трансформація з іншого проєкту відхиляється як не знайдена. Створення, зміна й тестування трансформацій і секретів потребує ключа `admin`; ключ `read` може їх переглядати.

## Що показує доставка {#deliveries}

Трансформація запускається один раз на доставку, під час її першої спроби. Те, що вона створила, зберігається разом із доставкою, і кожен повтор надсилає те саме тіло, наново підписане, із заголовками ендпоінта в тому вигляді, у якому вони є на момент цієї спроби. Облікові дані конвеєра ніколи не зберігаються: кожна спроба додає їх наново зі значення секрету на цей момент. [Повторна доставка](/docs/product-webhooks/deliveries#replay) знову запускає поточну версію трансформації.

У консолі відкрийте доставку на сторінці **Deliveries**. **Transformed by** називає трансформацію й версію, яка виконалася, а результат — один із таких:

- **Transformed**: тип вмісту, розмір, заголовки, які вона задала, назви облікових даних, які вона додала, і надіслане тіло.
- **Dropped**: доставку відкинув фільтр або скрипт повернув `null`, тож нічого не надіслано.
- **Failed**: чому запуск провалився. Доставка в dead-letter черзі.

Через API `GET /v1/deliveries/{id}/transform` повертає запуск або `null`, якщо трансформація не запускалася: `transformation_id`, `version`, `status` (`ok`, `dropped` або `failed`), `reason`, `error`, `body`, `content_type`, `header_names`, `credential_headers` і `credential_query` (назви, ніколи не значення) та `duration_ms`. Запуск скрипту також містить `logs` і `fuel`.

### Відкинуті доставки {#dropped}

Коли фільтр відкидає доставку або скрипт повертає `null`, нічого не надсилається й жодної спроби не робиться. Доставка отримує стан `sent` з `"dropped": true`, консоль показує її як **dropped**, а статистика ендпоінта й робочого простору рахує її окремо від доставлених: частку успішних доставок обчислюють серед тих, які мали бути надіслані. Відкидання — не невдача ні для ендпоінта, ні для трансформації. Проте до [місячної квоти доставок](/docs/product-webhooks#objects) така доставка зараховується, бо квота рахує кожну доставку тоді, коли її подію опубліковано.

## Коли запуск провалюється {#failures}

Конвеєр, який вдалося зберегти, усе одно може провалитися на конкретній події: `set`, що записав би щось усередину значення, яке не є обʼєктом (`set_conflict`), тіло чи значення понад [ліміт](#limits), значення, яке не може бути в заголовку, або облікові дані, чий секрет уже не існує (`secret_missing`) чи не може бути надісланий (`invalid_secret`). Той самий конвеєр на тій самій події провалюється так само, тож доставка одразу потрапляє в dead-letter чергу ненадісланою, з `last_error` на кшталт `pipeline_failed: step 2: set_conflict: …`.

Скрипт провалюється, коли кидає виняток, вичерпує час чи памʼять, заходить у надто глибоку рекурсію або повертає щось, що не є запитом (обʼєкт із `body` або `null`). Його доставка потрапляє в dead-letter чергу з `last_error`, що починається з `transform_failed:`.

Ми ніколи не надсилаємо замість цього подію без трансформації: отримувачем може бути стороння компанія, від якої трансформація якраз і має приховати дані.

Кожен невдалий запуск враховується для трансформації так само, як невдалі доставки — для ендпоінта, а запуск, який надсилає чи відкидає доставку, перериває серію. Після 20 невдач поспіль трансформація вимикається (**turned off after failures** у консолі, `auto_disabled` в API), доставки її ендпоінтів чекають, а ми надсилаємо лист власнику робочого простору й [операційний вебхук](/docs/product-webhooks/deliveries#operational) `transformation.disabled`. Виправте її, протестуйте й відновіть через **Resume** або надішліть `PATCH /v1/transformations/{id}` з `{"status": "enabled"}`: доставки, що чекали, буде надіслано, а ті, що потрапили в dead-letter чергу, можна [повторно доставити](/docs/product-webhooks/deliveries#replay).

## Ліміти {#limits}

Конвеєр не має циклів, годинника й вводу-виводу, тож той самий конвеєр на тій самій події завжди робить те саме, а фіксовані межі обмежують кожен запуск:

| Конвеєр | Ліміт |
|---|---|
| Кроки | 20 |
| Шляхи в `drop`, поля в `set`, назви в кожній частині кроку `headers` | 50 |
| Налаштування кроку як компактний JSON | 16 KiB |
| Примітка кроку | 200 символів |
| Вкладеність у кроці й у тілі | 32 рівні |
| Тіло, яке читає крок, і надіслане тіло | 256 KiB |
| Одне значення, яке формує крок | 64 KiB |
| Робота за один запуск | 100 000 прочитаних чи скопійованих значень; текст — одне на KiB |
| Заголовки наприкінці запуску | 50 |
| Значення одного заголовка | 8 KiB |
| Значення секрету | 8 192 символи |

| Скрипт | Ліміт |
|---|---|
| CPU | Близько 50 мс часу скрипту, які рахуються в інструкціях, а не вимірюються, тож той самий скрипт отримує той самий бюджет незалежно від того, наскільки ми завантажені |
| Загальний час | 1 секунда |
| Памʼять | 64 MiB |
| Розмір скрипту | 1 MiB |
| Результат | 256 KiB |
| Логи | 4 KiB |
| Одночасні скрипти на робочий простір | 2 на Starter, 4 на Pro; на Custom — як на плані, на якому побудовано договір |

## Помилки {#errors}

Конвеєр, який ніколи не зміг би виконатися, відхиляється під час збереження чи тестування з `422 invalid_pipeline`. Відмова називає першу проблему: `details.reason`, `details.path` (JSON Pointer до неї) і `details.step` (рахуючи з 0) — кожне, коли воно доречне.

```json
{ "error": { "code": "invalid_pipeline", "message": "…", "details": { "reason": "managed_header", "path": "/steps/0/headers/set/User-Agent", "step": 0 }, "request_id": "…" } }
```

| `reason` | Що не так |
|---|---|
| `invalid_document` | Це не обʼєкт із `version` і списком `steps`. |
| `unsupported_version` | `version` не дорівнює `1`. |
| `no_steps` | Кроків немає. |
| `too_many_steps` | Кроків понад 20. |
| `invalid_step` | Крок — не обʼєкт з одним ключем кроку, поруч із яким можуть бути лише `note` і, у фільтра, `action`. |
| `unknown_step` | Ключ кроку не є `filter`, `drop`, `set`, `map`, `headers` чи `auth`. |
| `invalid_value` | Налаштування не з тих, які приймає крок, як-от порожній `drop` чи примітка довша за 200 символів. |
| `invalid_path` | Шлях неможливо прочитати, або він містить символ підстановки там, де крок його не приймає. |
| `invalid_template` | Вираз неможливо прочитати, або він називає фільтр, якого не існує. |
| `invalid_filter` | Фільтр недійсний, наприклад має невідомий оператор. |
| `invalid_header` | Назва заголовка недійсна чи належить зʼєднанню, або значення не є друкованим ASCII в одному рядку. |
| `invalid_secret` | `secret` у кроці `auth` не є ідентифікатором секрету. Значення, вставлене туди, ніколи не повторюється в повідомленнях. |
| `auth_not_last` | Після кроку `auth` стоїть інший крок. |
| `too_deep` | Щось вкладено глибше ніж на 32 рівні. |
| `too_large` | Налаштування кроку перевищують 16 KiB. |
| `not_json` | Документ містить значення, яке не є JSON. |
| `managed_header` | Крок задає заголовок, який ми надсилаємо самі: `X-Webhook-*` чи `User-Agent`. |
| `forbidden_header` | Крок задає hop-by-hop чи керувальний заголовок, як-от `Expect`. |
| `unknown_secret` | Крок `auth` указує секрет, якого немає в його проєкті. |

Інші відмови:

| Статус | Код | Коли |
|---|---|---|
| `422` | `validation_error` | Трансформація з `code` і `pipeline` одночасно чи без жодного з них, або `PATCH` з полем іншого виду. |
| `402` | `not_entitled` (`feature: transformations`) | Створення скрипту, збереження нового коду, відновлення чи тестування скрипту на плані без скриптів. |
| `422` | `invalid_transformation` | Скрипт, що не завантажується: `syntax_error`, `no_transform`, `code_too_large` або `load_failed`. |
| `409` | `conflict` (`transformation_in_use`) | Видалення трансформації, яку ще виконує ендпоінт. Спершу відʼєднайте її. |
| `409` | `conflict` (`secret_in_use`) | Видалення секрету, який указує поточна версія конвеєра. Спершу змініть конвеєр. |
| `404` | `not_found` (`transformation`, `transformation_version`, `secret`) | Обʼєкта не існує, ця версія більше не зберігається, або ендпоінт указує трансформацію з іншого проєкту. |
| `429` | `rate_limited` | Перевищено 60 збережень і тестів скриптів на хвилину на робочий простір. |
| `503` | `unavailable` (`transform`) | Пісочниця не змогла виконати скрипт саме в той момент. Нічого не збережено; спробуйте ще раз. |
