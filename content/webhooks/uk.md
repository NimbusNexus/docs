# Вебхуки платформи

Вебхуки платформи — це спосіб, яким NimbusNexus повідомляє ваші системи про зміни: VM завершила розгортання, снапшот готовий, рахунок сформовано. Ви реєструєте URL, а ми щоразу, коли спрацьовує відповідна подія, надсилаємо на нього POST-запит із payload-ом у JSON.

> **Шукаєте продукт Webhooks?** Якщо ви хочете надсилати вебхуки *своїм власним* клієнтам — опублікувати подію, а ми підпишемо, повторимо й переграємо кожну доставку, — це окремий продукт, описаний на сторінці [Webhooks (продукт)](/docs/product-webhooks). Ця сторінка охоплює лише сповіщення, які NimbusNexus надсилає *вам* про вашу власну інфраструктуру. **Ці два механізми використовують різні заголовки підпису**, тож код перевірки не взаємозамінний.

Вебхуки дають змогу реагувати на зміни стану без опитування. Опитування працює, але у великому масштабі воно марнотратне (більшість запитів повертають «нічого не змінилося»), а в малому — повільне (про зміну ви дізнаєтеся лише під час наступного опитування). Вебхуки перевертають модель: ми повідомляємо вас тієї ж миті, коли щось відбувається.

## Як виглядає доставка {#delivery}

```http
POST /webhooks/nimbusnexus HTTP/1.1
Host: your-app.example.com
Content-Type: application/json
NN-Event: vm.created
NN-Delivery-Id: del_01HG7Y3...
NN-Timestamp: 1763410800
NN-Signature: sha256=4d2c8f19e6b07d3f...

{
  "event": "vm.created",
  "occurred_at": "2026-05-20T18:30:00Z",
  "data": {
    "id": "vm_01HG7Y3...",
    "name": "web-01",
    "state": "running",
    "ipv4": "203.0.113.5"
  }
}
```

Кожна доставка містить чотири заголовки:

- `NN-Event` — тип події (`vm.created`, `snapshot.completed` тощо)
- `NN-Delivery-Id` — унікальний для кожної доставки; його можна безпечно використовувати як ключ ідемпотентності на вашому боці
- `NN-Timestamp` — час доставки в секундах Unix epoch; використовується в підписі
- `NN-Signature` — HMAC-SHA256 від `{timestamp}.{body}` у шістнадцятковому кодуванні

## Перевірка підпису {#signature}

Підпис доводить, що доставка надійшла від NimbusNexus, а не від когось, хто вгадав URL вашого вебхука. Перевіряйте його в обробнику, перш ніж щось робити:

```ts
import crypto from 'node:crypto'

function verifyWebhook(req: Request, secret: string): boolean {
  const timestamp = req.headers.get('NN-Timestamp')!
  const signature = req.headers.get('NN-Signature')!.replace(/^sha256=/, '')
  const body = req.bodyText // raw body, not parsed JSON

  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${timestamp}.${body}`)
    .digest('hex')

  // Constant-time compare avoids timing oracles
  return crypto.timingSafeEqual(
    Buffer.from(signature, 'hex'),
    Buffer.from(expected, 'hex')
  )
}
```

Секрет ви отримуєте в дашборді під час створення ендпоінта вебхука. Зберігайте його в менеджері секретів, а не у вихідному коді — з ним будь-хто може підробити доставки.

Також відхиляйте доставки, timestamp яких відрізняється від часу на вашому сервері більш ніж на 5 хвилин. Це обмежує replay-вікно, якщо секрет колись витече.

## Типи подій {#events}

Кожен ресурс, що має життєвий цикл, генерує події. Поширені з них:

| Подія | Коли |
|---|---|
| `vm.created` | VM завершила розгортання й має стан `running` |
| `vm.state_changed` | VM перейшла з одного стану в будь-який інший |
| `vm.deleted` | VM знищено |
| `snapshot.completed` | Копіювання снапшота завершено |
| `backup.completed` | Запланований бекап завершено |
| `database.upgrade_completed` | Оновлення рушія керованої БД завершено |
| `floating_ip.attached` / `floating_ip.detached` | Зміни підʼєднання |
| `invoice.generated` | Місячний рахунок остаточно сформовано |
| `payment.succeeded` / `payment.failed` | Результати платежу |
| `quota.warning` | Проєкт перевищив 90 % будь-якої квоти |

Повний список типів подій наведено в довіднику API для кожного ресурсу (поле `events` ресурсу показує, які події він генерує).

## Семантика доставки {#delivery-semantics}

- **Щонайменше один раз.** Через нестабільну мережу чи повільний обробник ми можемо повторити доставку. Використовуйте `NN-Delivery-Id`, щоб дедуплікувати доставки на своєму боці.
- **Порядок не гарантується.** Дві події, що сталися з інтервалом ~1 секунда, можуть надійти не в тому порядку. Поле `occurred_at` у payload-і показує справжній порядок; якщо він важливий, сортуйте за ним.
- **Повтори:** невдалі доставки (відповідь не 2xx або тайм-аут > 10 с) повторюються з експоненційним backoff через 1, 5, 25, 125 і 625 секунд. Усього пʼять спроб. Після цього доставку відкидають; 14 днів вона відображається на панелі «failed deliveries» у дашборді.
- **Тайм-аут:** ваш обробник має 10 секунд, щоб повернути 2xx. Якщо потрібно зробити більше роботи, поставте її в чергу й одразу підтвердьте отримання вебхука.
