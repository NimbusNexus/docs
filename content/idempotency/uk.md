# Ідемпотентність

Запит **ідемпотентний**, якщо, зробивши його двічі, ви отримуєте той самий ефект, що й від одного разу. `GET /v1/vms` ідемпотентний за своєю природою — він нічого не змінює. `POST /v1/vms` за своєю природою **не** ідемпотентний — викличте його двічі, і отримаєте дві VM.

Заголовок `Idempotency-Key` дає змогу зробити будь-який запит, що змінює дані, таким, який можна безпечно повторити. Передайте будь-яке унікальне значення (зазвичай це UUID), і ми закешуємо відповідь на 24 години та повертатимемо ту саму відповідь на кожен повтор із тим самим ключем.

## Яку проблему це розвʼязує {#problem}

Ви викликаєте `POST /v1/vms`. На зворотному шляху мережа обривається, і замість 201 ви отримуєте тайм-аут. VM створилася? Ви не знаєте:

- Якщо повторите: можливо, отримаєте дві VM (оригінальний запит вдався, а ваш повтор створив другу).
- Якщо не повторите: можливо, не отримаєте жодної VM (оригінальний запит не вдався, а ви прийняли хибний стан).

З ключем ідемпотентності повтор безпечний. Якщо оригінальний запит вдався, повтор поверне той самий 201 з тим самим ідентифікатором VM — без дубліката. Якщо оригінальний запит не вдався, повтор справді виконає роботу.

## Як використовувати заголовок {#usage}

Надішліть будь-який рядок довжиною до 255 символів:

```bash
curl -X POST {{API_BASE_URL}}/v1/vms \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Idempotency-Key: 8e1c91a4-04d0-4d77-8e6e-2f7c1a5b8e84" \
  -H "Content-Type: application/json" \
  -d '{ "name": "web-01", "size": "gp-2-4", "region": "us-east-1", "image": "ubuntu-24.04" }'
```

Заведено використовувати один UUID v4 на одну логічну операцію. Згенеруйте його один раз на клієнті, збережіть до надсилання запиту й використовуйте повторно під час кожного повтору тієї самої логічної операції. Для *наступної* логічної операції згенеруйте новий.

## Що означає «той самий ключ» {#same-key}

Ми кешуємо відповідь за ключем, який складається з таких частин:

1. Значення заголовка `Idempotency-Key`
2. API-ключ, з яким зроблено запит
3. Ендпоінт (метод + шлях)

Тож два запити отримують ту саму кешовану відповідь, лише якщо **збігаються всі три**. Це запобігає випадковостям — ключ, повторно використаний на двох ендпоінтах, із двома API-ключами чи навіть у двох проєктах (різні API-ключі), не спричинить плутанини.

## Що кешується {#cached}

Ми кешуємо **повну відповідь** — код статусу, заголовки, тіло. Повтор із тим самим ключем повертає побайтово ідентичний результат. Це важливо для клієнтів, які обчислюють відбитки відповідей, щоб визначити, «чи щось змінилося», — вони отримують узгоджену відповідь.

Ми також кешуємо **помилки**. Якщо ваш перший виклик не пройшов валідацію (`422 validation_error`), повтор поверне той самий `422`, а не іншу помилку, навіть якщо між спробами ви щось виправили. Так і має бути: ідемпотентність означає «той самий ефект», а ефектом першого виклику була невдача. Якщо хочете нову спробу, згенеруйте новий ключ.

Виняток — API Webhooks: він записує ключ лише тоді, коли публікація вдається. Див. розділ [В API Webhooks](#webhooks).

TTL кешу — **24 години** від першого використання. Після цього запит із тим самим ключем вважається новим запитом.

## Коли його використовувати {#when}

| Тип ендпоінта | Використовувати? |
|---|---|
| `POST`, що створює ресурс (`POST /v1/vms`) | Так |
| `PUT`, що замінює ресурс (`PUT /v1/vms/{id}`) | Так |
| `PATCH`, що оновлює ресурс | Так |
| `DELETE` | Так |
| `GET`, `HEAD`, `OPTIONS` | Ні — вони й так ідемпотентні за своєю природою |
| `POST`, що запускає одноразову операцію (напр. `POST /v1/vms/{id}/reboot`) | Так — перезапустити двічі не те саме, що перезапустити один раз |

На практиці: ключ корисний для будь-якого запиту, що змінює дані й може обірватися на півдорозі. Ціна — заголовок у кожному запиті й генерування UUID на вашому боці.

## Конфлікт із попереднім використанням {#conflicts}

Якщо ви повторно використаєте ключ з **іншим тілом запиту** на тому самому ендпоінті, то отримаєте `409 Conflict` з `error.code: 'conflict'`, а `error.message` повідомить, що ключ уже використано з іншим тілом запиту. Оригінальний запит лишається в силі; ваше інше тіло відхиляється. Це найбезпечніша поведінка — якби ми мовчки повертали стару відповідь, це приховало б баг у вашому циклі повторів.

Якщо вам справді потрібно зробити інший запит, згенеруйте новий ключ.

Попередні версії цієї сторінки стверджували, що ця відповідь містить `error.code: 'idempotency_key_reused'`. API ніколи не надсилав цього коду; він надсилає `conflict`. `conflict` охоплює й інші зіткнення з наявним станом, як-от уже зайняту назву; в API Webhooks для цього випадку `details.reason` дорівнює `idempotency_key_reuse`. Див. сторінку [Помилки](/docs/errors#codes-state).

## В API Webhooks {#webhooks}

В API Webhooks `Idempotency-Key` застосовується до публікації події (`POST /v1/events`) і поводиться так:

| Ви надсилаєте | Ви отримуєте |
|---|---|
| Новий ключ | `201` і нову подію, розгалужену на відповідні ендпоінти. |
| Той самий ключ і те саме тіло | `200`, **оригінальну** подію й заголовок `Idempotency-Replayed: true`. Повторного розгалуження немає. |
| Той самий ключ та інше тіло | `409` з `error.code: 'conflict'`, `details.reason: 'idempotency_key_reuse'` і ключем у `details.idempotency_key`. Оригінальна подія лишається в силі. |
| Той самий ключ після запиту, що не вдався | Запит виконується знову. Невдала публікація (помилка валідації, помилка квоти, ліміт запитів) не записує ключ. |

«Те саме тіло» означає той самий тип події й payload для того самого проєкту. Ключ належить вашому робочому простору й проєкту, а не API-ключу, який його надіслав, тож два API-ключі, що публікують в один проєкт, мають спільні ключі. Ключ зберігається щонайменше 24 години.

## Коли можна обійтися без нього {#skip}

Без ключа діє `best-effort retry`. Для читання цього достатньо; для записів, де ви можете змиритися з «можливо, нічого, можливо, один» (операції, ідемпотентні на рівні застосунку), — теж. Заголовок нічого не коштує, але якщо ваш застосунок не повторює запити після збою, різниці ви не помітите.

Випадки, коли ключ вам справді потрібен:

- Усе, що повʼязане з білінгом (щоб не списати кошти з картки двічі)
- Усе, що бачить користувач (щоб не надіслати сповіщення двічі)
- Будь-який крок робочого процесу, що розгортає ресурси в разі збою (щоб не лишилося осиротілих ресурсів)
