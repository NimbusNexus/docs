# Ідемпотентність

Запит **ідемпотентний**, якщо, зробивши його двічі, ви отримуєте той самий ефект, що й від одного разу. `GET /api/v1/instance/` ідемпотентний за своєю природою — він нічого не змінює. `POST /api/v1/instance/` за своєю природою **не** ідемпотентний — викличте його двічі, і отримаєте дві VM.

Заголовок `Idempotency-Key` дає змогу безпечно повторити запит, але лише на кількох маршрутах, які його приймають. Усі інші маршрути ігнорують цей заголовок.

## Яку проблему це розвʼязує {#problem}

Ви публікуєте подію через `POST /v1/events`. На зворотному шляху мережа обривається, і замість 201 ви отримуєте тайм-аут. Подію опубліковано? Ви не знаєте:

- Якщо повторите: можливо, ваші клієнти отримають її двічі (оригінальний запит вдався, а ваш повтор опублікував другу).
- Якщо не повторите: можливо, вони її так і не отримають (оригінальний запит не вдався, а ви прийняли хибний стан).

З ключем ідемпотентності повтор безпечний. Якщо оригінальний запит вдався, повтор поверне оригінальну подію, і повторного розгалуження не буде. Якщо оригінальний запит не вдався, повтор справді виконає роботу.

## Маршрути, що приймають заголовок {#usage}

| Маршрут | API | Ключ |
|---|---|---|
| `POST /v1/events` | Webhooks | Необовʼязковий |
| `POST /v1/qr-tracked/imports` | QR-коди | Обовʼязковий |
| `POST /api/v1/payment/payment_methods/{payment_method_id}/add_funds` | Інфраструктура | Обовʼязковий |

Надішліть будь-який унікальний рядок:

```bash
curl -X POST {{WEBHOOKS_BASE_URL}}/v1/events \
  -H "Authorization: Bearer $WEBHOOKS_API_KEY" \
  -H "Idempotency-Key: 8e1c91a4-04d0-4d77-8e6e-2f7c1a5b8e84" \
  -H "Content-Type: application/json" \
  -d '{ "event_type": "order.created", "payload": { "order_id": "1234" } }'
```

Заведено використовувати один UUID v4 на одну логічну операцію. Згенеруйте його один раз на клієнті, збережіть до надсилання запиту й використовуйте повторно під час кожного повтору тієї самої логічної операції. Для *наступної* логічної операції згенеруйте новий.

## В API Webhooks {#webhooks}

В API Webhooks `Idempotency-Key` застосовується до публікації події (`POST /v1/events`) і поводиться так:

| Ви надсилаєте | Ви отримуєте |
|---|---|
| Новий ключ | `201` і нову подію, розгалужену на відповідні ендпоінти. |
| Той самий ключ і те саме тіло | `200`, **оригінальну** подію й заголовок `Idempotency-Replayed: true`. Повторного розгалуження немає. |
| Той самий ключ та інше тіло | `409` з `error.code: 'conflict'`, `details.reason: 'idempotency_key_reuse'` і ключем у `details.idempotency_key`. Оригінальна подія лишається в силі. |
| Той самий ключ після запиту, що не вдався | Запит виконується знову. Невдала публікація (помилка валідації, помилка квоти, ліміт запитів) не записує ключ. |

«Те саме тіло» означає той самий тип події й payload для того самого проєкту. Ключ належить вашому робочому простору й проєкту, а не API-ключу, який його надіслав, тож два API-ключі, що публікують в один проєкт, мають спільні ключі. Ключ зберігається щонайменше 24 години.

## В API QR-кодів і під час поповнення балансу {#other-routes}

В API QR-кодів для масового імпорту (`POST /v1/qr-tracked/imports`) потрібен ключ. Ключ належить вашому робочому простору. Той самий ключ і те саме тіло повертають оригінальний імпорт, не створюючи його коди повторно; на той самий ключ з іншим тілом API відповідає `409`.

Для поповнення балансу (`POST /api/v1/payment/payment_methods/{payment_method_id}/add_funds`) ключ теж потрібен, щоб повторне поповнення не списало кошти з картки двічі. Цей виклик потребує сесії, у яку ви ввійшли, а не API-ключа ([Способи оплати](/docs/api/payment-methods)).

## Конфлікт із попереднім використанням {#conflicts}

В API Webhooks і QR-кодів, якщо ви повторно використаєте ключ з **іншим тілом запиту** на тому самому ендпоінті, то отримаєте `409 Conflict` з `error.code: 'conflict'`, а `error.message` повідомить, що ключ уже використано з іншим тілом запиту. Оригінальний запит лишається в силі; ваше інше тіло відхиляється. Це найбезпечніша поведінка — якби ми мовчки повертали стару відповідь, це приховало б баг у вашому циклі повторів.

Якщо вам справді потрібно зробити інший запит, згенеруйте новий ключ.

Попередні версії цієї сторінки стверджували, що ця відповідь містить `error.code: 'idempotency_key_reused'`. API ніколи не надсилав цього коду; він надсилає `conflict`. `conflict` охоплює й інші зіткнення з наявним станом, як-от уже зайняту назву; в API Webhooks для цього випадку `details.reason` дорівнює `idempotency_key_reuse`. Див. сторінку [Помилки](/docs/errors#codes-state).

## На всіх інших маршрутах {#skip}

Без ключа перевіряйте, перш ніж повторювати запит на запис:

- **Створення VM або тому.** Виклик ставить роботу в чергу й відповідає без ідентифікатора, тож шукайте новий ресурс у списку (`GET /api/v1/instance/`, `GET /api/v1/storage/`), перш ніж надсилати запит знову. З унікальним `name` його легко знайти.
- **Створення чогось з унікальною назвою.** На DNS-зону чи контейнер обʼєктного сховища, назва яких уже зайнята, API відповідає `409`, тож повтор після тайм-ауту не створить другого такого ресурсу. Сприймайте `409` як ознаку того, що оригінальний запит, можливо, вдався.
- **Видалення.** Повторне видалення більше нічого не видаляє, хоча другий виклик може відповісти помилкою, бо ресурсу вже немає. Щоб переконатися, прочитайте ресурс.

Запити на читання завжди можна повторювати.
