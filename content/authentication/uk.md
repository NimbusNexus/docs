# Автентифікація

API NimbusNexus використовує **API-ключі** як bearer-токени. Механізм один для всіх ендпоінтів — без окремого формату облікових даних для кожного ресурсу й без окремої схеми підпису для «просунутих» викликів. Якщо ви можете зробити один автентифікований запит, ви можете зробити їх усі.

## Як виглядає запит {#request-shape}

Надсилайте ключ у заголовку `Authorization`. Формат — саме слово `Bearer`, а після нього ваш ключ:

```bash
curl {{API_BASE_URL}}/v1/vms \
  -H "Authorization: Bearer nn_live_xxxxxxxxxxxxxxxx"
```

Префікс ключа залежить від середовища: `nn_live_*` для продакшну, `nn_test_*` для пісочниці. Після префікса йдуть 32–48 символів із безпечного алфавіту base32.

## Генерування ключа {#generating}

У дашборді: **Settings → API keys → New key**. Значення ключа показується рівно один раз — під час створення, тож скопіюйте його одразу. Після цього дашборд показує лише префікс і останні 4 символи, щоб ви могли розрізняти ключі, не розкриваючи секрет.

API для створення API-ключів навмисно немає. Щоб відновитися після компрометації одного ключа, потрібен окремий канал, до якого скомпрометований ключ не дістане, — і саме необхідність іти в дашборд є тим вузьким місцем, яке робить таке відновлення чистим.

## Привʼязка до проєкту {#project-scope}

Кожен API-ключ привʼязаний до **одного проєкту**. Ключ може читати й записувати ресурси свого проєкту, але не бачить ресурсів інших проєктів, навіть у тому самому акаунті.

Проєкт — це одиниця керування доступом, білінгу та ізоляції. Для індивідуальної розробки достатньо проєкту за замовчуванням, який створюється разом із новим акаунтом; командам, що працюють із продакшном, зазвичай потрібен окремий проєкт для кожного середовища (`prod`, `staging`, `dev`), щоб скомпрометований dev-ключ не дістав до продакшн-даних.

Змінити проєкт = згенерувати новий ключ у цільовому проєкті. Механізму «використовуйте цей ключ, але вдавайте, що ви в іншому проєкті» немає: він підірвав би гарантію ізоляції.

## Області дії (можливості) {#scopes}

Ключі мають **області дії**, які обмежують, що ключ може робити у своєму проєкті. За замовчуванням новий ключ має право читання й запису для всього в проєкті; під час створення цей набір можна звузити, напр. лише до `vms:read` для агента моніторингу, якому ніколи не треба створювати ресурси.

Повний список областей дії відповідає типам ресурсів:

- `vms:read`, `vms:write`, `vms:create`, `vms:delete`
- `databases:read`, `databases:write`, …
- `block-storage:read`, `block-storage:write`, …
- `object-storage:read`, `object-storage:write`, …
- `iam:read`, `iam:write` (керування користувачами, проєктами й самими ключами)

Запит до ендпоінта, якому потрібна область дії, якої ключ не має, отримує `403 Forbidden` з `error.code: 'forbidden'`, а `error.message` пояснює, чого бракує. Тож можна без зайвих витрат почати з вузьких областей дії й розширювати їх лише тоді, коли щось не спрацює. (Попередні версії цієї сторінки обіцяли `scope_required` з областю дії в `error.fields.scope`; API ніколи не надсилав ні того, ні іншого.)

## Ротація {#rotation}

Кожен ключ можна ротувати незалежно від інших. Ротація ключа:

1. Генерує нове значення ключа.
2. Позначає старий ключ як **застарілий**, але залишає його чинним ще **24 години**.
3. Протягом цього вікна записує в журнал використання обох ключів, щоб ви могли переконатися, що новий ключ уже використовується, перш ніж старий перестане діяти.

Для автоматичної ротації (ми її рекомендуємо) викликайте API IAM за розкладом, і 24-годинне перекриття поглине вікно розгортання. Інструменти, які тримають ключ довго (CI/CD, розгорнуті агенти), мають перечитувати його під час запуску процесу, щоб ротація поширювалася за один цикл розгортання.

Якщо підозрюєте, що ключ скомпрометовано, **відкличте** його замість ротації — так ви пропускаєте 24-годинний пільговий період, і старий ключ одразу стає недійсним. У дашборді ключ відкликається одним кліком; для програмного екстреного відкликання є також ендпоінт IAM.

## Типові помилки {#errors}

API Webhooks і Inboxes відповідають на проблему з обліковими даними такими кодами. Вони відрізняються в одному: `invalid_credential`, тобто ключ, якого API не розпізнає, — це `403` у Webhooks і `401` в Inboxes.

| Статус | error.code | API | Що це означає |
|---|---|---|---|
| 401 | `unauthorized` | Обидва | Облікові дані не надіслано (ні `Authorization`, ні `X-API-Key`), або ключ відкликано. |
| 401 / 403 | `invalid_credential` | Обидва | Ключ або токен недійсний: `401` в Inboxes, `403` у Webhooks. Замініть його: повторне надсилання не допоможе. |
| 403 | `forbidden` | Обидва | Ключ дійсний, але цього не може: бракує області дії чи ролі, ключ, обмежений певними проєктами, використано поза ними або продукт не ввімкнено для вашого робочого простору. |

`message` пояснює, який саме випадок стався; розгалужуйте обробку за `code`, а не за статусом: `invalid_credential` — це `403` у Webhooks і `401` в Inboxes. Обробляйте його разом з `unauthorized` як «ці облікові дані не годяться».

Попередні версії цієї сторінки наводили `no_credentials`, `invalid_credentials`, `expired_credentials`, `scope_required` і `wrong_project`. API ніколи не надсилали цих кодів. Вони надсилають `unauthorized` там, де сторінка писала `no_credentials`; `invalid_credential` там, де вона писала `invalid_credentials` або `expired_credentials`, бо прострочений ключ — це ключ, який API не може перевірити; і `forbidden` там, де вона писала `scope_required` або `wrong_project`.

Помилки вище мають стандартний формат, описаний на сторінці [Помилки](/docs/errors).

## Що далі {#next-steps}

- Прочитайте сторінку [Угоди](/docs/conventions) про правила, яких дотримується кожен ендпоінт (ідентифікатори ресурсів, пагінація, помилки, ідемпотентність).
- Прочитайте довідник [Віртуальні машини](/docs/api/vms) — конкретний розібраний приклад API ресурсу.
- Для взаємодії між сервісами у вашій власній інфраструктурі можна також створювати **відносини довіри** між проєктами — див. довідник IAM (незабаром).
