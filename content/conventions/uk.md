# Угоди

NimbusNexus має два види API, і не всі угоди в них спільні. **API інфраструктури** на `{{API_HOST}}` (VM, мережі, сховище, DNS і ваш акаунт) має маршрути під `/api/v1/` і приймає API-ключ у заголовку `X-API-Key` ([Автентифікація](/docs/authentication)). Кожен з **API застосунків** (Webhooks, Inboxes, Request Bins та інші) має власний базовий URL із маршрутами під `/v1/` і приймає ключ як bearer-токен ([Налаштування REST API](/docs/setup/rest)). Ця сторінка вказує, де ці два види відрізняються.

## Ідентифікатори ресурсів {#resource-ids}

В API інфраструктури більшість ідентифікаторів ресурсів — це UUID, як-от `3f0c9e1a-6b7d-4c2e-9a51-7d2b8f4e1c60`; контейнери й обʼєкти обʼєктного сховища ідентифікуються за назвою. В API застосунків ідентифікатори мають префікс, як-от `ep_` для ендпоінта Webhooks чи `evt_` для події. Вважайте будь-який ідентифікатор непрозорим рядком.

Ідентифікатори не змінюються протягом усього життя ресурсу — їх ніколи не використовують повторно й не переписують під час перейменування. Використовуйте їх в URL-адресах, зовнішніх ключах і журналах аудиту, а зрозумілі людині поля `name` — лише для відображення.

## Пагінація {#pagination}

У Webhooks, Inboxes і Request Bins ендпоінти списків приймають два параметри query:

- `limit` — розмір сторінки. За замовчуванням 50, максимум 200. Понад 200 запит не проходить валідацію: `422` `validation_error` ([Помилки](/docs/errors#codes-validation)).
- `offset` — скільки елементів пропустити. Тіло відповіді повертає наступне значення як `next_offset`; щоб перейти далі, передайте його назад як `offset`.

Патерн у коді:

```bash
# Page 1
curl '{{WEBHOOKS_BASE_URL}}/v1/endpoints?limit=50' \
  -H "Authorization: Bearer $WEBHOOKS_API_KEY"

# Page 2 (offset from page 1's response.next_offset)
curl '{{WEBHOOKS_BASE_URL}}/v1/endpoints?limit=50&offset=50' \
  -H "Authorization: Bearer $WEBHOOKS_API_KEY"
```

Якщо `next_offset` дорівнює null, ви на останній сторінці.

В API інфраструктури більшість ендпоінтів списків, як-от `GET /api/v1/instance/`, відповідають цілим списком і не приймають параметрів пагінації. Ті, що розбивають список на сторінки, роблять це одним із двох способів:

- `limit` і `marker` (останній ідентифікатор чи назва, які ви бачили): образи VM, DNS-зони й набори записів, контейнери й обʼєкти обʼєктного сховища.
- `limit` і `offset`: бекапи томів, розклади бекапів, підключення до зовнішніх сховищ, сповіщення.

```bash
# Page 1
curl '{{API_BASE_URL}}/api/v1/zones/?limit=50' \
  -H "X-API-Key: $NIMBUS_KEY"

# Page 2 (marker: the id of the last zone on page 1)
curl '{{API_BASE_URL}}/api/v1/zones/?limit=50&marker=<zone-id>' \
  -H "X-API-Key: $NIMBUS_KEY"
```

## Помилки {#errors}

Ці два види API повідомляють про помилки по-різному. В API інфраструктури помилка містить `success: false` і `message`:

```json
{
  "success": false,
  "message": "Authentication required"
}
```

Помилка валідації (`422`) натомість містить `errors` із полями, які не пройшли перевірку:

```json
{
  "success": false,
  "errors": {
    "field": ["Invalid value"]
  }
}
```

Кодів помилок тут немає: розгалужуйте обробку за статусом і не розбирайте `message`. Кожна відповідь має заголовок `X-Request-ID`; додавайте його, коли звертаєтеся в підтримку.

Кожна відповідь із помилкою від Webhooks, Inboxes і Request Bins має такий формат JSON:

```json
{
  "error": {
    "code": "validation_error",
    "message": "request validation failed",
    "details": {
      "errors": [
        {
          "loc": ["body", "event_type"],
          "msg": "Field required",
          "type": "missing"
        }
      ]
    },
    "request_id": "7e4b1d9c2a6f4e8b9d3c5a1f0e2b4c68"
  }
}
```

- `code` — стабільний машинозчитуваний рядок. Розгалужуйте обробку за ним, а не за кодом статусу, коли той самий статус має кілька значень (напр. `402` може бути `quota_exceeded`, `not_entitled` або `workspace_frozen`).
- `message` — зрозумілий людині англійський текст для логів. Не локалізується; якщо показуєте помилку кінцевим користувачам, зіставте `code` з власним текстом.
- `details` — є для деяких кодів. У помилці валідації `details.errors` перелічує вхідні дані, які не пройшли перевірку; у багатьох інших помилках це поле містить `reason`, що уточнює код, разом зі значеннями, які до нього належать. Його формат залежить від коду.
- `request_id` — є в кожному тілі помилки, яке надсилає API: це той самий ідентифікатор, що й у заголовку `X-Request-ID`, який має кожна відповідь API. Відповідь від edge-рівня перед API (напр. `502` чи `504` або `413` для тіла, надто великого, щоб дійти до API) не містить ні тіла помилки API, ні заголовка `X-Request-ID` ([Помилки](/docs/errors#request-id)). Записуйте його в логи й додавайте, коли звертаєтеся в підтримку.
- `next_code` — надсилається лише тоді, коли код перейменовують: це код, який ця помилка матиме після перейменування. Якщо він є, розгалужуйте обробку за ним замість `code`. Зараз жоден код не перейменовують, тому API його не надсилає.

Сторінка [Помилки](/docs/errors) перелічує всі коди й причини та вказує, який з API, Webhooks чи Inboxes, надсилає кожен із них. (Попередні версії цієї сторінки показували `validation_failed` як `400` з `fields` і `request_id` у тілі. Перших двох API ніколи не надсилали: помилка валідації — це `422` `validation_error` з `details`. `request_id` тоді в тілі теж не було; тепер тіла помилок API його містять.)

## Коди статусу HTTP {#status-codes}

Ми використовуємо невеликий передбачуваний набір:

| Статус | Коли |
|---|---|
| `200` | Успіх, є тіло. В API інфраструктури — також запит, роботу якого поставлено в чергу ([Тривалі операції](#operations)). |
| `201` | Ресурс створено. |
| `202` | Прийнято: робота завершується після відповіді ([Тривалі операції](#operations)). |
| `204` | Успіх, без тіла (типово для DELETE). |
| `400` | Запит не вдалося прочитати в тому вигляді, у якому його надіслано. `error.message`, а в API інфраструктури `message`, пояснює чому. |
| `401` | Немає придатних облікових даних. Див. сторінку [Автентифікація](/docs/authentication). |
| `402` | В API застосунків: запит блокує ваш план або стан білінгу (квота, функція, якої немає у вашому плані, заморожений робочий простір). Повтор не допоможе. |
| `403` | Автентифіковано, але не авторизовано (бракує області дії, не той проєкт тощо). У Webhooks — також облікові дані, яких він не приймає. В API інфраструктури — також виклик поза правилами доступу API-ключа. |
| `404` | Ресурсу не існує, АБО той, хто викликає, не може його бачити. Ми навмисно не розрізняємо ці випадки — розкриття того, що ресурс існує, саме по собі є витоком доступу. |
| `409` | Конфлікт стану (назва вже зайнята, `Idempotency-Key` повторно використано з іншим тілом тощо). |
| `413` | Тіло перевищує ліміт розміру. |
| `422` | Валідація не пройшла. У помилці валідації (`validation_error`) `error.details.errors` перелічує вхідні дані, які не пройшли перевірку; в інших кодах `422` API Webhooks, як-от `invalid_payload` чи `unknown_event_type`, це обʼєкт, який називає хибне значення або порушене правило. В API інфраструктури `errors` містить поля, які не пройшли перевірку. |
| `429` | Перевищено ліміт запитів. Якщо `Retry-After` задано, він указує, коли повторити запит. |
| `500–504` | Проблема на боці сервера. Ідемпотентні запити завжди можна безпечно повторити. |

## Ідемпотентність {#idempotency}

Кілька маршрутів приймають заголовок `Idempotency-Key`, щоб повтор не виконував роботу двічі. У Webhooks це публікація події. Передайте будь-яке унікальне значення (зазвичай це UUID):

```bash
curl -X POST {{WEBHOOKS_BASE_URL}}/v1/events \
  -H "Authorization: Bearer $WEBHOOKS_API_KEY" \
  -H "Idempotency-Key: 8e1c91a4-04d0-4d77-8e6e-2f7c1a5b8e84" \
  -H "Content-Type: application/json" \
  -d '{ "event_type": "order.created", "payload": { "order_id": "1234" } }'
```

Усі інші маршрути ігнорують цей заголовок. В API інфраструктури дворазове створення VM дає дві VM — із ключем чи без нього. Сторінка [Ідемпотентність](/docs/idempotency) перелічує маршрути, які його приймають, і пояснює, що робити на решті.

GET-ендпоінти завжди ідемпотентні, і заголовок їм не потрібен.

## Тривалі операції {#operations}

Деякі дії не завершуються в межах запиту. В API інфраструктури вони відповідають, щойно роботу поставлено в чергу:

- `POST /api/v1/instance/` (створення VM) відповідає `200` з `{"success": true}`, без ідентифікатора.
- `POST /api/v1/storage/` (створення тому) відповідає `201`, без ідентифікатора.
- `POST /api/v1/instance/{instance_id}/resize` відповідає `200`, і VM переходить у `VERIFY_RESIZE`.
- `PUT` і `DELETE` для набору DNS-записів відповідають `202`.

Обʼєкта операції, за яким можна було б стежити, немає. Щоб стежити за роботою, читайте ресурс і дивіться на його `status`: `GET /api/v1/instance/` показує нову VM у стані `BUILD`, потім `ACTIVE` або `ERROR`. Опитування зараховується в ліміти запитів як звичайний виклик API.

## Timestamp-и {#timestamps}

Усі timestamp-и мають формат **RFC 3339 / ISO 8601 в UTC** із суфіксом `Z`:

```text
2026-05-19T18:30:00Z
```

Ніколи не місцевий час, ніколи не зі зсувом часового поясу, ніколи не ціле число epoch (окрім заголовків підпису вебхуків, які містять Unix timestamp, бо такої угоди дотримуються ті, хто підписує HMAC). `Date.parse()` у JavaScript і відповідні парсери зі стандартних бібліотек інших мов розбирають цей формат без додаткового коду.
