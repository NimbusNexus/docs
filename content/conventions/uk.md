# Угоди

API має одну форму, яка повторюється для кожного ресурсу. Знаючи цю форму, ви знаєте кожен ендпоінт — від ресурсу до ресурсу змінюється лише набір полів самого ресурсу.

## Ідентифікатори ресурсів {#resource-ids}

Кожен ресурс має стабільний непрозорий ідентифікатор у форматі `<prefix>_<26-char-base32>`:

| Ресурс | Префікс | Приклад |
|---|---|---|
| Віртуальна машина | `vm_` | `vm_01H8FZQ4XW9KMP4XQNR3VT7DC2` |
| Керована база даних | `db_` | `db_01H8FZQ4XW9KMP4XQNR3VT7DC2` |
| Блоковий том | `vol_` | `vol_01H8FZQ4XW9KMP4XQNR3VT7DC2` |
| Снапшот | `snap_` | `snap_01H8FZQ4XW9KMP4XQNR3VT7DC2` |
| API-ключ | `key_` | `key_01H8FZQ4XW9KMP4XQNR3VT7DC2` |

Ідентифікатори не змінюються протягом усього життя ресурсу — їх ніколи не використовують повторно й не переписують під час перейменування. Використовуйте їх в URL-адресах, зовнішніх ключах і журналах аудиту, а зрозумілі людині поля `name` — лише для відображення.

## Пагінація {#pagination}

Ендпоінти списків приймають два параметри query:

- `limit` — розмір сторінки. За замовчуванням 50, максимум 200. Понад 200 запит не проходить валідацію: `422` `validation_error` ([Помилки](/docs/errors#codes-validation)).
- `cursor` — непрозорий вказівник на наступну сторінку. Якщо сторінок більше, тіло відповіді повертає його як `pagination.next_cursor`; щоб перейти далі, передайте його назад як `cursor`.

Курсори непрозорі — не намагайтеся їх декодувати чи складати самі. Вони містять стан сортування й фільтрів з початкового запиту, тому зміна фільтрів посеред пагінації призводить до невизначеної поведінки. Коли фільтри змінюються, починайте спочатку (без `cursor`).

Патерн у коді:

```bash
# Page 1
curl '{{API_BASE_URL}}/v1/vms?limit=50' \
  -H "Authorization: Bearer $NIMBUS_KEY"

# Page 2 (cursor from page 1's response.pagination.next_cursor)
curl '{{API_BASE_URL}}/v1/vms?limit=50&cursor=eyJpZCI6...' \
  -H "Authorization: Bearer $NIMBUS_KEY"
```

Якщо `pagination.next_cursor` відсутній або дорівнює null, ви на останній сторінці.

## Помилки {#errors}

Кожна відповідь із помилкою має той самий формат JSON:

```json
{
  "error": {
    "code": "validation_error",
    "message": "request validation failed",
    "details": {
      "errors": [
        {
          "loc": ["body", "event_type"],
          "msg": "Field required",
          "type": "missing"
        }
      ]
    },
    "request_id": "7e4b1d9c2a6f4e8b9d3c5a1f0e2b4c68"
  }
}
```

- `code` — стабільний машинозчитуваний рядок. Розгалужуйте обробку за ним, а не за кодом статусу, коли той самий статус має кілька значень (напр. `402` може бути `quota_exceeded`, `not_entitled` або `workspace_frozen`).
- `message` — зрозумілий людині англійський текст для логів. Не локалізується; якщо показуєте помилку кінцевим користувачам, зіставте `code` з власним текстом.
- `details` — є для деяких кодів. У помилці валідації `details.errors` перелічує вхідні дані, які не пройшли перевірку; у багатьох інших помилках це поле містить `reason`, що уточнює код, разом зі значеннями, які до нього належать. Його формат залежить від коду.
- `request_id` — є в кожному тілі помилки, яке надсилає API: це той самий ідентифікатор, що й у заголовку `X-Request-ID`, який має кожна відповідь API. Відповідь від edge-рівня перед API (напр. `502` чи `504` або `413` для тіла, надто великого, щоб дійти до API) не містить ні тіла помилки API, ні заголовка `X-Request-ID` ([Помилки](/docs/errors#request-id)). Записуйте його в логи й додавайте, коли звертаєтеся в підтримку.
- `next_code` — надсилається лише тоді, коли код перейменовують: це код, який ця помилка матиме після перейменування. Якщо він є, розгалужуйте обробку за ним замість `code`. Зараз жоден код не перейменовують, тому API його не надсилає.

Сторінка [Помилки](/docs/errors) перелічує всі коди й причини та вказує, який з API, Webhooks чи Inboxes, надсилає кожен із них. (Попередні версії цієї сторінки показували `validation_failed` як `400` з `fields` і `request_id` у тілі. Перших двох API ніколи не надсилали: помилка валідації — це `422` `validation_error` з `details`. `request_id` тоді в тілі теж не було; тепер тіла помилок API його містять.)

## Коди статусу HTTP {#status-codes}

Ми використовуємо невеликий передбачуваний набір:

| Статус | Коли |
|---|---|
| `200` | Успіх, є тіло. |
| `201` | Ресурс створено. Заголовок `Location` вказує на новий ресурс. |
| `202` | Операцію прийнято; щоб стежити за прогресом, перевіряйте `operation.status`. |
| `204` | Успіх, без тіла (типово для DELETE). |
| `400` | Запит не вдалося прочитати в тому вигляді, у якому його надіслано. `error.message` пояснює чому. |
| `401` | Немає придатних облікових даних. Див. сторінку [Автентифікація](/docs/authentication). |
| `402` | Запит блокує ваш план або стан білінгу (квота, функція, якої немає у вашому плані, заморожений робочий простір). Повтор не допоможе. |
| `403` | Автентифіковано, але не авторизовано (бракує області дії, не той проєкт тощо). У Webhooks — також облікові дані, яких він не приймає. |
| `404` | Ресурсу не існує, АБО той, хто викликає, не може його бачити. Ми навмисно не розрізняємо ці випадки — розкриття того, що ресурс існує, саме по собі є витоком доступу. |
| `409` | Конфлікт стану (назва вже зайнята, `Idempotency-Key` повторно використано з іншим тілом тощо). |
| `413` | Тіло перевищує ліміт розміру. |
| `422` | Валідація не пройшла. У помилці валідації (`validation_error`) `error.details.errors` перелічує вхідні дані, які не пройшли перевірку; в інших кодах `422` API Webhooks, як-от `invalid_payload` чи `unknown_event_type`, це обʼєкт, який називає хибне значення або порушене правило. |
| `429` | Перевищено ліміт запитів. Якщо `Retry-After` задано, він указує, коли повторити запит. |
| `500–504` | Проблема на боці сервера. Ідемпотентні запити завжди можна безпечно повторити. |

## Ідемпотентність {#idempotency}

Ендпоінти, що змінюють дані (POST, PUT, PATCH, DELETE), приймають необовʼязковий заголовок `Idempotency-Key`. Передайте будь-яке унікальне значення (зазвичай це UUID); ми кешуємо відповідь на 24 години й повертаємо ту саму відповідь на повторний запит із тим самим ключем.

```bash
curl -X POST {{API_BASE_URL}}/v1/vms \
  -H "Authorization: Bearer $NIMBUS_KEY" \
  -H "Idempotency-Key: 8e1c91a4-04d0-4d77-8e6e-2f7c1a5b8e84" \
  -H "Content-Type: application/json" \
  -d '{ "name": "web", "size": "gp-2-4", "region": "us-east-1", "image": "ubuntu-24.04" }'
```

Використовуйте ключі ідемпотентності, коли ваш клієнт може повторити запит після мережевого збою, але не може визначити, чи вдався оригінальний запит. Без ключа поведінка за замовчуванням — «повтор без гарантій»; з ключем повтори безпечні.

GET-ендпоінти завжди ідемпотентні, і заголовок їм не потрібен.

## Тривалі операції {#operations}

Деякі дії не завершуються в межах життєвого циклу запиту:

- `POST` для VM повертає `202`, поки гіпервізор виділяє інстанс.
- `POST` для бази даних повертає `202`, поки піднімаються репліки.
- Зміна розміру тому й міграція VM повертають `202`.

Тіло будь-якої відповіді 202 містить обʼєкт `operation`:

```json
{
  "id": "vm_01H8FZQ4XW9KMP4XQNR3VT7DC2",
  "state": "provisioning",
  "operation": {
    "id": "op_01H8FZ...",
    "kind": "vm_create",
    "status": "running",
    "progress": 0.4,
    "started_at": "2026-05-19T18:30:00Z"
  }
}
```

Стежити за прогресом можна двома способами:

1. **Опитування** — `GET /v1/operations/{op_id}` раз на секунду. Дешево; зараховується в ліміти запитів як звичайний виклик API.
2. **Вебхук** — підпишіть URL зворотного виклику в дашборді. Ми надсилаємо POST, коли операція досягає кінцевого стану (`succeeded` або `failed`).

Більшість операцій завершуються менш ніж за 60 секунд. Винятки — завантаження образу VM під час першого використання (~90 секунд) і налаштування кластера Kafka (~180 секунд).

## Timestamp-и {#timestamps}

Усі timestamp-и мають формат **RFC 3339 / ISO 8601 в UTC** із суфіксом `Z`:

```text
2026-05-19T18:30:00Z
```

Ніколи не місцевий час, ніколи не зі зсувом часового поясу, ніколи не ціле число epoch (окрім заголовків підпису вебхуків, які містять Unix timestamp, бо такої угоди дотримуються ті, хто підписує HMAC). `Date.parse()` у JavaScript і відповідні парсери зі стандартних бібліотек інших мов розбирають цей формат без додаткового коду.
