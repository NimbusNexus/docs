# Політика версіонування

API NimbusNexus має версію **v1** і залишатиметься на v1 безстроково. Несумісні зміни не виходять поверх v1 — вони вийшли б у новій версії (`v2` тощо), а v1 і далі працювала б без змін. Такого самого підходу до версіонування дотримуються Stripe, Twilio й AWS для своїх основних API.

## Що таке несумісна зміна {#breaking}

Усе, через що наявний код може перестати працювати:

- Видалення ендпоінта
- Видалення поля з відповіді
- Видалення коду статусу з можливих відповідей ендпоінта
- Перейменування поля
- Зміна типу поля (напр. `string` → `number`)
- Зміна поведінки наявного ендпоінта за замовчуванням
- Посилення валідації запитів (тіло, яке раніше приймалося, тепер відхиляється)
- Додавання нового обовʼязкового параметра запиту

На `v1` такого ніколи не буває. Крапка.

> **Оновлено 2026-10-15.** До запуску v1 написання помилок, які вже перебували в процесі перейменування, і кілька змін, що їх супроводжували, набули чинності без 12-місячного періоду, описаного нижче. В Inboxes: `invalid_request`, `unauthorized`, який API надсилав для ключа, якого не розпізнає або не може перевірити, його загальний `error`, причина `project` для `forbidden` і ключі `details` `max_inboxes`, `max_http_bins`, `monthly_messages`, `plan` та `inbox_id`. У Webhooks: `internal`, `unprocessable` і `plan_violation`, `402`, який API надсилав для `max_attempts` понад стелю плану, і його `409` для масового реплею (обидва тепер `422`), а також його `details` валідації й типи записів. Також видалено два поля відповідей Inboxes: `paid_plans_enabled` у `GET /v1/plan`, яке на той час дорівнювало `true` для кожного робочого простору, і `project_id` скриньки, якого API вже не заповнював. На сторінці [Помилки](/docs/errors#renames) показано відповідність для кожної зміни помилок. Від запуску v1 кожна зміна відбувається за правилами цієї сторінки.

## Що таке адитивна зміна {#additive}

Що ми випускаємо на `v1` без попередження:

- Нові ендпоінти
- Нові необовʼязкові параметри запиту
- Нові поля у відповідях (під час розбору слід ігнорувати невідомі поля)
- Нові коди помилок (невідомі значення `error.code` слід обробляти за сімейством коду статусу)
- Нові типи подій вебхуків
- Нові значення enum (невідомі значення enum слід вважати непрозорими)
- Нові коди статусу з того сімейства, яке ендпоінт уже повертає

Адитивні зміни ми описуємо в [журналі змін](/changelog), але не ховаємо за прапорцем. Наявний код продовжує працювати; новий код може ними скористатися.

## Пряма сумісність — як писати код, що витримає зміни {#forward-compat}

Три правила:

**1. Ігноруйте невідомі поля під час розбору.** Нове поле у відповіді не повинно спричиняти помилку у вашому клієнті. Більшість бібліотек JSON так і поводяться за замовчуванням.

```ts
// Correct
const { id, name, state } = await res.json()

// Wrong (will reject responses with new fields)
const allowedKeys = ['id', 'name', 'state']
for (const k of Object.keys(json)) {
  if (!allowedKeys.includes(k)) throw new Error('unknown field')
}
```

**2. Вважайте невідомі значення enum непрозорими.** Якщо ви розгалужуєте обробку за `state`, обробляйте відомі значення, а для невідомих показуйте сирий рядок і не падайте.

```ts
switch (vm.state) {
  case 'running': return 'green'
  case 'stopped': return 'gray'
  case 'provisioning': return 'amber'
  default: return 'gray' // Don't throw, don't assume — we may add 'migrating'
}
```

**3. Розгалужуйте обробку за `error.code`, а не за `status`.** Коди статусу групують помилки (`4xx` чи `5xx`); `error.code` їх розрізняє. Ми можемо додавати нові коди до наявних кодів статусу; ваш код має обробляти їх у гілці за замовчуванням, а не вважати нерозпізнані коди фатальними багами.

## Політика застарівання {#deprecation}

Ми дуже стараємося, щоб на v1 це не знадобилося. Якщо ми все ж позначимо ендпоінт чи поле як застаріле:

- Ендпоінт чи поле працюватиме без змін **щонайменше 12 місяців**
- До відповідей додається заголовок `Deprecation` (RFC 9745)
- Заголовок `Sunset` містить дату кінця підтримки
- Дашборд показує використання застарілих ендпоінтів у кожному проєкті

Дванадцять місяців — це довго. На практиці від запуску на v1 ще жодного разу нічого не позначали як застаріле — адитивного розвитку вистачає для більшості потреб.

## Коли вийде v2 {#v2}

Якщо ми колись випустимо v2 (найближчим часом не плануємо), розгортання виглядатиме так:

- v2 запускається на `/v2/...` поруч із `/v1/...` — обидві працюють паралельно
- v1 і далі отримує виправлення багів і нові (адитивні) функції щонайменше 24 місяці
- v2 має окремий базовий URL (`{{API_BASE_URL}}/v2/...`), тож сам URL указує на версію

Ви мігруєте, коли будете готові, а не коли вас змусять. Шлях такий: почати використовувати ендпоінти `/v2` у новому коді й переводити старий код у власному темпі — одномоментного cutover у призначений день не буде.

## Чому це важливо {#why}

Хмарна платформа, API якої ламається кожні два роки, — не надійна інфраструктура. Чому v1 переживе більшість інших контрактів платформи: код клієнтів, партнерські інтеграції й розповсюдження SDK залежать від стабільності цієї поверхні. Зламати її без попередження — найшвидший спосіб утратити довіру.

Якщо ви колись побачите справжню несумісну зміну на `v1`, яка не вийшла в новій версії, — це баг. Повідомте про нього в підтримку, і ми його виправимо.
