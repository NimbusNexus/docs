# Ліміти запитів

API інфраструктури обмежує, скільки запитів він приймає за хвилину. API застосунків обмежують окремі дії, як-от публікацію події. В обох випадках на запит понад ліміт API відповідає `429`, зазвичай із заголовком `Retry-After`, який каже, скільки секунд зачекати.

## API інфраструктури {#defaults}

Кожен запит до `{{API_HOST}}` зараховується в бюджет запитів на хвилину:

| Хто викликає | Запитів на хвилину | Рахується окремо для |
|---|---|---|
| Сесія, у яку ви ввійшли (`Authorization: Bearer` або cookie сесії) | 120 | Кожного користувача |
| API-ключ або виклик без облікових даних | 60 | Кожної IP-адреси |

API-ключ не має власного бюджету. Ключі, які використовують з однієї адреси, ділять її 60 запитів на хвилину між собою і з усім іншим, що надсилає запити звідти. `GET /api/v1/notifications/list` має нижчий ліміт — 30 на хвилину, і він рахується за тим самим лічильником.

Хвилина відлічується від вашого першого запиту, і це не ковзне вікно: коли вона закінчується, лічильник знову починає з нуля.

## Заголовки відповіді {#headers}

Відповіді API інфраструктури містять ліміт, який застосовано, і те, що від нього лишилося:

```http
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 59
```

Понад ліміт відповідь — `429` з `X-RateLimit-Remaining: 0` і заголовком `Retry-After`, який у секундах показує, скільки лишилося до кінця хвилини:

```json
{
  "success": false,
  "message": "Too many requests. Please try again later."
}
```

## API застосунків {#apps}

API застосунків не надсилають заголовків `X-RateLimit` і обмежують не кожен запит. Дії, які вони обмежують, понад ліміт відхиляються з `429` `rate_limited`, як описано на сторінці [Помилки](/docs/errors#codes-rate):

- **Webhooks:** публікація (`POST /v1/events`) обмежена частотою публікацій вашого плану, окремо для кожного робочого простору. Повторне надсилання й реплей (`POST /v1/deliveries/{delivery_id}/redeliver`, `POST /v1/deliveries/redeliver`, `POST /v1/deliveries/replay` і `POST /v1/events/{event_id}/replay`) обмежені тією самою частотою, але з власним лічильником. Для вхідних подій на `POST /v1/ingest/{source_id}` ліміт — 600 на хвилину на джерело, а потім — частота публікацій вашого плану ([Що бачить провайдер](/docs/product-webhooks/sources#responses)). Для збереження й тестування скриптів ліміт — 60 на хвилину на робочий простір ([Трансформації](/docs/product-webhooks/transformations#errors)).
- **Inboxes:** кожна скринька приймає пошту до ліміту на хвилину, який задає ваш план ([Ліміти за планами](/docs/product-inboxes#limits)).
- **Request Bins:** bin може надсилати 10 тестів пересилання на хвилину ([Протестуйте URL пересилання](/docs/product-bins/reference#forward-test)). URL bin-а приймає 120 запитів на хвилину від одного відправника й 600 на хвилину загалом ([Що відповідає URL bin-а](/docs/product-bins/reference#edge-answers)).
- **Transforms:** запуски й тести мають спільний ліміт запусків на хвилину, який задає ваш план, окремо для кожного робочого простору, і в кожному процесі сервера в робочого простору одночасно можуть виконуватися щонайбільше два з них ([Плани й ліміти](/docs/product-transforms/reference#limits)).
- **QR-коди:** робочий простір може надсилати 10 тестів вебхуків на хвилину.

## Стратегія backoff {#backoff}

Правильний патерн, коли ви отримуєте `429`:

```ts
async function callWithBackoff(fn: () => Promise<Response>) {
  for (let attempt = 0; attempt < 5; attempt++) {
    const res = await fn()
    if (res.status !== 429) return res

    const retryAfter = Number(res.headers.get('Retry-After') ?? '1')
    // Jitter prevents the thundering-herd problem if many clients
    // hit the limit at the same moment and all retry exactly together
    const jitter = Math.random() * 0.5 * retryAfter
    await new Promise(r => setTimeout(r, (retryAfter + jitter) * 1000))
  }
  throw new Error('Rate limit exceeded after 5 retries')
}
```

Два зауваження:

- **Завжди дотримуйтеся `Retry-After`.** Не повторюйте раніше: ви лише отримаєте ще один `429`.
- **Додавайте jitter**, якщо викликаєте API з кількох воркерів. Без нього вони всі повторюють запит в один і той самий момент і разом знову впираються в ліміт.

## Що вважається запитом {#counted}

В API інфраструктури зараховується кожен HTTP-виклик, зокрема:

- `GET`-запити, як-от `GET /api/v1/instance/`
- Кожна сторінка [списку з пагінацією](/docs/pagination) і кожне опитування, поки ви чекаєте на перехід VM в `ACTIVE`
- Невдалі виклики, як-от `401`, і самі `429`

Щоб не перевищувати ліміт з однієї адреси, розподіляйте роботу в часі: опитуйте рідше й не запитуйте списки того, що можна прочитати один раз і зберегти.

## Як підвищити ліміти {#raising}

Жоден виклик API чи налаштування плану не підвищує ці ліміти. Якщо ваш ліміт заважає реальному навантаженню, [зверніться в підтримку]({{BASE_URL}}/contact/support).
